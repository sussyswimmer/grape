# Architecture

## Big picture

```
┌──────────────────────── Grape (Tauri 2 app, tray-only) ──────────────────────────┐
│                                                                                   │
│  grape-platform ──(DragSignal stream)──▶ app: WheelController ──▶ overlay window  │
│   macOS / Windows                         (state machine,           (ui/: SVG     │
│   drag + modifier + cursor                 INTERACTION_SPEC §1)      wheel)       │
│                                                 │                       │         │
│                                                 │◀── DragDropEvent ─────┘         │
│                                                 │    Enter/Over/Drop/Leave        │
│                                                 ▼                                 │
│                                   grape-core: targets(), hit_test(), plan()       │
│                                                 │  JobPlan                        │
│                                                 ▼                                 │
│                                   grape-engines: run(plan) ──▶ sidecars / crates  │
│                                                 │  progress events                │
│                                                 ▼                                 │
│                                   toast + output file next to source              │
└───────────────────────────────────────────────────────────────────────────────────┘
```

## Crates and their contracts

### `grape-core` (pure Rust: no I/O except path *strings*, no OS, no Tauri)
- `Format`: enum of the 45 inputs plus the one target-only format, `html` (46 in all, in `FORMAT_MATRIX.md` table order). Includes `from_extension()`, `from_file_name()`, `display_name()`, `category()` and `output_ext()`.
- `targets(format) -> &'static [Format]`: the conversion matrix across all tiers, in doc order. `targets_enabled(format, features)`, `pair_tier(from, to)` and `pairs(features)` apply tiers.
- `tools(format, selection_len) -> Vec<ToolKey>`: tools per format, with the multi-select filter applied. `tool_tier(tool, format)` and `tools_enabled(format, selection_len, features)` apply tiers.
- `actions() -> &'static [ActionKey; 6]`. Titles come from `ActionKey::title(Platform)`.
- `output_name(source, &Operation, taken: &HashSet<String>) -> String`: the naming rules, with case-insensitive collisions. Page helpers: `produces_pages`, `pages_folder_name`, `page_file_name`.
- `wheel_layout(n) -> Vec<Segment>` and `hit_test(dx, dy, n) -> Option<usize>`: geometry from `INTERACTION_SPEC.md` §4. `GEOMETRY` exposes the constants to the UI, and `clamp_anchor(anchor, work_area)` implements §3.
- `wheel_content(items, mode, features) -> WheelContent`: what each wheel shows, or which empty state.
- `plan(&Selection, &Operation, &Settings) -> Result<JobPlan, PlanError>`: a list of `Job { inputs, output: JobOutput, op, used_fallback }`. The tool's `ToolParams` travel inside `op`, and `JobOutput` is `File`, `Folder` or `PagesFileOrFolder`. The `Selection` carries a `DirSnapshot { names, writable }` per folder the plan may write to, so core does no I/O. `grape_engines::build_selection` reads the sources' folders only when outputs go next to them, and the fallback folder only when a plan may write there (D16), so a Mac drop doesn't ask for folders Grape won't write to. **No execution.**
- `Tier` gating: `Features { v2, later }` decides whether v2/later items appear. The full tables stay in the data and are filtered at the edge. See `DECISIONS.md` D12.

### `grape-engines` (executes `JobPlan`s)
- One `Engine` trait per family: `ImageEngine`, `MediaEngine` (FFmpeg), `PdfEngine`, `ArchiveEngine`, `SubtitleEngine`, `DocEngine` (v2).
- Each engine reports progress (0–1, optional) and supports cancellation.
- Engines write to a temp file in the destination folder, then do an atomic rename to the final name. A failed job leaves nothing behind.
- **[Grape]** The final rename must never replace an existing file (no-clobber: `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING`, `renamex_np(RENAME_EXCL)` on macOS). If the name was taken after planning, re-plan the name. `grape-core`'s collision check can't see every way two names match on disk (e.g. Unicode normalization), so this is the last guard for golden rule 2 (`DECISIONS.md` D12).
- Sidecar binaries are located via a `SidecarPaths` value injected by the app. Never hardcode paths.
- **Helper processes.** Decoders Grape doesn't trust in its own process run in a child process, one per job, killed on cancel or timeout: the PDF worker (`Grape --grape-pdf-worker`, PDFium, D29), bsdtar for RAR (D27), and the image helper for HEIC and AVIF (D33, D41): `grape-heif.exe` on Windows (Grape's own GPL sidecar on libheif, with dav1d and libaom for AVIF, built from `tools/grape-heif`) and `Grape --grape-heif-worker` on macOS (ImageIO through `grape-platform`, and rav1e for AVIF output, under a 2 GiB heap bound), and the SVG worker (`Grape --grape-svg-worker`, resvg, D39) on every OS, which arms its own 2 GiB heap bound and draws on a 64 MiB stack. The PDF and image helpers and the SVG worker take one JSON request on stdin and answer with JSON lines on stdout; the SVG worker's protocol is its own (`svg/protocol.rs`), not the image helper's. The image helper's parent is `heif.rs`, the SVG worker's `svg/run.rs` and the PDF worker's `pdf/run.rs`, all on `helper.rs`'s process plumbing (bsdtar has its own pump, `archive/rar/bsdtar.rs`). The image helper's and the SVG worker's pixels go through a raw file (`pixels.rgba`) in a private `grape-heif-…` or `grape-svg-…` folder under the OS temp folder, never the pipe and never the user's folder. The folder goes when the job ends, and one that a crash or a kill left behind goes at Grape's next start (`remove_stale_work_dirs` sweeps both prefixes). The app's `main.rs` and the engine's two test binaries (`src/bin/grape-pdf-worker.rs`, `src/bin/grape-svg-worker.rs`) each install a copy of the `WorkerHeap` allocator the heap bound needs: change all three together.
- **Containment hook.** `grape_engines::set_contain(Arc<dyn Contain>)`, set once by the app at startup (`contain.rs`), puts each helper process into an OS container right after it starts, before its request is written, bsdtar before it's given a byte of the RAR, and each `ffmpeg` and `ffprobe` run (D22) right after it starts, before its output is read: a Job Object on Windows (`grape_platform::windows::job`: 2 GiB for the image helper, 2.5 GiB for the SVG worker, 6 GiB for the PDF worker, 1 GiB for bsdtar and no cap for FFmpeg; killed with Grape, one process, no error dialogs, UI limits unless Grape itself runs in a job). A helper or bsdtar that ends without a result after committing 90% of its cap "needs too much memory" (`helper::near_memory_cap`). It's a process-wide hook, not an `EngineCtx` field, so `EngineCtx` keeps D16's shape; tests pass a fake straight to the engine. A helper or bsdtar that can't be contained is killed and its job fails. FFmpeg fails open: a run that can't be contained runs on, and the reason reaches the log only when that run or its output check fails (D22).

### `grape-heif-proto` (pure: the image helper protocol, D33; protocol 2 adds AVIF, D41)
- The request (`{protocol, workDir, op, limits}`, where an encode names its format, `heic` or `avif`), the JSON-line messages (`image`, `progress`, then `done` or `error`; the probe's caps per format), the raw pixel file, the `ftyp` sniff (HEIC, AVIF, other HEIF, not HEIF), and the worker loop `serve` / `worker_main` behind a `Codec` trait. `std`, `serde` and `serde_json` only, no `unsafe`, no OS crate.
- Three programs share it: `grape-engines` (the parent), the app's `main.rs` on macOS (the worker, with `grape-platform`'s ImageIO codec) and `tools/grape-heif` (the Windows worker). Any change bumps `PROTOCOL` and rebuilds `grape-heif` in the same commit.
- `tools/grape-heif` is **outside the workspace**, with its own `Cargo.lock`, `deny.toml` and `about.toml`: it links GPL code (x265), so nothing of it may enter Grape's own binaries (golden rule 6). CI builds it and bundles it beside `Grape.exe`.

### `grape-webp` (libwebp's encoder, D28)
- `encode(Pixels, &Options, keep_going) -> Result<Vec<u8>, Error>` and `version()`: 8-bit RGB or RGBA in, libwebp's whole RIFF file out, lossy (VP8 at a quality and method, alpha lossless) or lossless (VP8L at a preset level, exact). `keep_going(percent)` is libwebp's progress hook, run inside `catch_unwind`; false cancels. Sides of 1 to 16,383 and data of exactly the pixels' size are checked before libwebp sees them.
- libwebp 1.6.0, vendored by libwebp-sys `=0.14.4` and compiled by its build script with the system's C compiler, links into Grape itself: no sidecar. Encode only, so no file a user dropped ever reaches libwebp; Grape reads WebP with image-webp.
- It holds the only `unsafe` code for images, so `grape-engines` keeps `#![forbid(unsafe_code)]`. Every libwebp allocation has a drop guard. `grape-engines`' `imagetool/webp_compress.rs` calls it for Compress on WebP (D28).

### `grape-platform` (OS glue, `#[cfg(target_os)]` modules)
- `DragMonitor` (`start(SyncSender<DragSignal>)`, `stop()`): emits `DragSignal::{Started{modifiers}, Moved{x,y}, Modifiers(Modifiers), Escape, Ended}` on a bounded channel, and drops signals rather than block. `Started` carries the keys already held, which don't open a wheel (`DECISIONS.md` D14). The pure `tracker::DragTracker` holds the drag rules; the Windows hook thread and worker feed it. `drag_monitor()` returns the one for this OS. `mock::ScriptedMonitor` replays scripts for tests.
- `display_bounds_at(x, y) -> Result<DisplayBounds, PlatformError>`: the monitor under the point, as `DisplayBounds { monitor: Rect, work_area: Rect, scale: f64 }` in global coordinates. Those are physical pixels on Windows (`rcMonitor`, `rcWork`). On macOS they're points from the top-left of the primary screen, with `scale` 1.0, read from a screen cache that the main thread refreshes, with a CoreGraphics fallback (D18). The overlay is sized to `monitor`, and the anchor is clamped to `work_area`.
- `windows::install_drop_target(hwnd, sink)`: Grape's own `IDropTarget` on the overlay and its child windows. It sends `DropEvent::{Enter{paths,x,y}, Over{x,y}, Leave, Drop{paths,x,y}}` and never reports a move (`DECISIONS.md` D13).
- `macos::{harden_window, frame_and_show, describe_window}` (main thread only): the overlay's and the toast's NSWindow level, Spaces behavior, and a show that never makes the window key (D18).
- `macos::{show_panel, hide_panel, WindowRole::Panel}` (main thread only): the tool panel at level 99, under the toast (100) and the overlay (101). `show_panel(ns_window, frame) -> PanelShown { front_pid }` records the app in front, sets the frame, `orderFrontRegardless`, `makeKeyWindow`, then asks macOS to activate Grape; `hide_panel(ns_window, back_to_pid) -> bool` orders it out and, if it was key, hands activation back (D31). `macos::mouse_button_down()` (any thread) tells the app whether an Esc the page got belongs to a drag.
- `file_actions`: share, copy, copyPath, move, terminal. Float lives in the app because it's a window. Built on Windows (M5) and macOS (D18): `copy_files(paths)`, `copy_paths(paths)`, `open_terminal(dir, app)` (the `terminal_app` setting), `move_to_chosen_folder(paths) -> MoveOutcome::{Cancelled, AlreadyThere{to}, Moved{to, moved: Vec<MovedItem{from, now}>, unsure, of}}`, `reveal(path)` and `share(paths, near) -> ShareOutcome { opened, skipped: Vec<Skipped { path, why: SkipReason::{Folder, Missing, Unshareable} }> }`. Share is the share sheet on Windows, opened near `near` (global physical pixels; the app passes the wheel's center), with files only (D21). On macOS it's AirDrop with every item, `near` is ignored and nothing is skipped. Each returns `Unsupported` where it isn't built (everything on other OSes). The app's `actions.rs` runs them on a thread of their own and writes the toasts.
- `windows::{harden_shelf, show_shelf, hide_shelf}` and `windows::drag_out(hwnd, paths) -> DragOut { outcome: DragOutcome, skipped }`, on the main thread, which owns the shelf: the float shelf's window styles, a show that never activates it, and its drag out, which offers copy or link and never move (D21). `windows::primary_button_down()` tells the app's snap timer whether a button is held. On macOS (D43): `harden_window(…, WindowRole::Shelf)` (level 3 and the `Closable` bit), `macos::{show_shelf, hide_shelf, window_frame}` (a show that's never key or activating and records the app in front, a hide that hands activation back to the app the user was last in, the frame in points), `macos::follow_app_activations()` (once at launch on the main thread: observes the workspace's app activations for that hide) and `macos::drag_out(ns_window, items, ended) -> DragStart::{Started, NotStarted(DragOutcome)}`, an AppKit dragging session that offers copy or link and calls `ended` from the source's end callback. `DragOutcome::{Copied, Linked, Cancelled, ButtonUp, NothingToDrag}` and `DragItem { path, folder }` are at the crate root, shared by both OSes.
- `windows::{harden_panel, show_panel, hide_panel, other_app_foreground, raise_topmost, reframe_overlay, escape_down}`, for the tool panel (D31): `harden_panel` gives it the shelf's bits (a tool window that a click activates); `show_panel(hwnd, frame)` shows it topmost without activating it; `hide_panel(hwnd, back_to) -> HandBack::{NotActive, HandedBack, Refused, NoWindow}` hands the foreground back to `back_to` (from `other_app_foreground()`, never one of Grape's windows) if the panel is in front, then hides it (the decision is the pure `win_rules::hand_back_plan`, tested on every OS); `raise_topmost(hwnd)` lifts a window to the top of the topmost band, and `reframe_overlay(hwnd, frame) -> Reframed { rect, reframed }` puts the shown overlay back on its frame (the decision is the pure `win_rules::reframe`); `escape_down()` reads Esc with `GetAsyncKeyState`, never consuming it. `other_app_foreground` and `escape_down` work on any thread; the rest run on the window's thread.
- `windows::run_value(name, exe) -> RunValue::{Missing, MissingTurnedOff, ThisExe, OtherExe, Unreadable}` (any thread): reads, never writes, HKCU's and HKLM's `Run` value `name` and Task Manager's `StartupApproved\Run` record for it, so the app can register launch at login again after a reinstall (D19). The decision is the pure `win_rules::run_value_of`, tested on every OS.
- `haptic_tick()`: a light trackpad tick on macOS, a no-op elsewhere.
- `keys` and `shortcuts`, for the Shortcuts wheel (D47): `KeyCode` and `Chord` (a key by its place on the keyboard, with the hotkey rules), `hotkey_monitor()` (`HotkeyMonitor`: `HotkeySignal::{Pressed(id, PressContext), Released(id)}` for `HotkeyId::{Open, Escape, Confirm}`), `pointer_watch()` (`PointerWatch`: `PointerSignal::{Moved, Down, Up}` only while it's switched on), and the calls a step makes: input access, posting keys and text, the clipboard, opening things, the program a script step runs, system controls, moving another app's window, handing the front back, and the app and file pickers. The signatures are in `docs/design/m10-shortcuts-wheel.md` §3 and §4. Built on macOS (`PLATFORM_MACOS.md` → "Shortcuts wheel"); on Windows and every other OS each one answers `Unsupported`. `mock::{ScriptedHotkeys, ScriptedPointer}` replay scripts for tests.
- `macos::heif::ImageIo`: the image helper worker's codec (`grape_heif_proto::Codec`, D33, D41), run only in the worker process: ImageIO decodes HEIC and AVIF and writes HEIC; `avif::encode` (rav1e through ravif, feature `avif-encode`, on in the app's macOS build only) writes AVIF. `windows::job::JobGuard::assign(child, max_memory)`: the Job Object the app's `contain.rs` puts each helper into.
- `file_actions::pick_folder(owner, title, start)`: the native folder picker for Settings, sharing Move's code. It runs on a blocking worker thread (D19).
- See `PLATFORM_MACOS.md` / `PLATFORM_WINDOWS.md`.

### `apps/desktop/src-tauri` (the app)
- Owns the windows: **overlay** (wheel), **settings**, **toast**, the tool **panel**, and on Windows and macOS the **float shelf** (`float.rs`; built on first use on Windows, D21, and hidden at launch on macOS, D43). The shelf's model is in memory only: items in drop order, no path twice, at most 50. Its page gets ids and names, never paths.
- The **panel** (`panel.rs`, its pure model in `panel/model.rs`, D31) is declared hidden in `tauri.conf.json`: a tool window that a click activates, never focused when shown, one at a time (a new request replaces the open one). A drop on Compress, Audio Channels, Normalize Volume or Merge PDFs (grape-core's `ToolKey::has_v1_panel`) opens it only when the wheel offers the tool for that drop (`model::offered`: `wheel_content` with the features `plan` uses, so Audio Channels opens on one file and Merge PDFs on two or more) and this build can run it (`jobs::check_runnable`, the check the direct path uses too). `GRAPE_PREVIEW_PANELS=1` skips only the second. Its page gets a request seq, item ids and display names, never paths, and answers by seq and ids; Rust checks every run, builds the `Operation` with `ToolParams` and the items in the chosen order, and starts the job. It refuses the page's cancel while a mouse button is down (that Esc belongs to a drag), and on Windows the Esc poll acts only until the panel's window first has the focus. Every show and hide is one main-thread reconcile, never Tauri's `show`, `hide` or `set_focus`.
- Runs the `WheelController` state machine and bridges platform signals, UI events and engines.
- The **Shortcuts wheel** (`shortcuts/`, D47) is a fourth wheel on the same controller and the same overlay: `State::Shortcuts`, opened by a hot key instead of a drag (`INTERACTION_SPEC.md` §12). `model.rs` is the pure part (menus, shortcuts, steps, validation, which menu shows), `store.rs` its file, `session.rs` one open wheel, `run.rs` the runner behind an `Actuator` trait, and `mod.rs` the wiring: `ShortcutsState`, the commands, the hot keys and the one run at a time. Every type that holds something the user typed writes its own `Debug`, printing kinds and counts only. The contract is `docs/design/m10-shortcuts-wheel.md`.
- Exposes Tauri commands to the UI, each granted only to the window that uses it (`capabilities/`): `wheel_painted` (overlay), `toast_clicked` (toast), the `settings_*` commands and the 17 `shortcuts_*` commands (Settings, `capabilities/settings.json`), `float_view`, `float_remove`, `float_clear`, `float_reveal` and `float_drag_out` (the shelf), and `panel_current`, `panel_run` and `panel_cancel` (the panel, `capabilities/panel.json`). `float_drag_out` is async and queues the drag on the main thread; the panel's three are async too. So are the `shortcuts_*` commands: each is one edit of the model that answers the whole view, and none of them runs a shortcut. The Settings page never sends a path (apps, files and folders are picked on the Rust side), but it does send what the user typed for a shortcut: names, text, scripts and links (D47). A command exists in three places that tests keep equal and in one order: `build.rs`' list, `generate_handler!` in `lib.rs` and the capability's permissions; no other window's capability may hold a `shortcuts_*` permission.
- Stores settings with `tauri-plugin-store` and handles launch at login with `tauri-plugin-autostart`.

### `apps/desktop/ui` (TypeScript)
- `overlay.ts` renders the wheel SVG from `Segment[]`, highlights from controller events, plays the tick sound. A Shortcuts wheel is one more content kind, `shortcuts`, with the user's names and icons (an emoji, or a glyph from `wheel/glyphs.ts`, Grape's own drawings).
- `settings.ts` is the settings window. It mounts two roots: `#settings-root` (`mountSettings`) and `#shortcuts-root` (`mountShortcuts`, with `settings/shortcuts-model.ts` and `settings/shortcuts-view.ts`), the Shortcuts section, which has its own command queue and status line and talks only through the `shortcuts_*` commands.
- `panel.html` and `panel.ts` (with `panel/model.ts`, `panel/copy.ts` and `panel/view.ts`) are the tool panel. It shows what `panel://open` sends and answers with `panel_run` or `panel_cancel` by seq and item ids.
- `float.html` and `float.ts` (with `float/model.ts` and `float/view.ts`) are the shelf. It lists what `float://view` sends, and a press on an item that moves 4 px becomes one `float_drag_out` call with ids. Rust runs the OS drag.
- The UI never decides behavior. It renders what Rust sends and reports pointer/drop info back.

## The overlay window (the hard part)

Requirements:
1. Transparent, borderless, always on top (including over full-screen apps on macOS), with no taskbar or dock entry, and it never steals focus.
2. While the wheel is open it **covers the whole display** under the cursor, so every drop lands in Grape and an off-ring drop can cancel cleanly (`INTERACTION_SPEC.md` §6).
3. It's a drop target that receives file paths and the cursor position during the drag.

Plan:
- One Tauri `WebviewWindow` labelled `overlay`, created hidden at startup with `transparent(true)`, `decorations(false)`, `always_on_top(true)`, `skip_taskbar(true)`, `focused(false)`, `focusable(false)` (on Windows this is what sets `WS_EX_NOACTIVATE`), `shadow(false)` and `visible_on_all_workspaces(true)`. On Windows, `grape_platform::windows::harden_overlay` adds `WS_EX_TOOLWINDOW` and keeps shows from activating the window through a subclass, because tao rewrites the extended style on every show and hide (`DECISIONS.md` D11). `"macOSPrivateApi": true` stays in `tauri.conf.json`; it has been a no-op since Tauri 2.12.1 (the transparency APIs are always on), but tauri-build still requires the matching `macos-private-api` Cargo feature.
- When opened on Windows: `set_position`/`set_size` to the display's frame, then `show()`. On Windows the overlay is then raised to the top of the topmost band on every show (`raise_topmost`), so an open panel or shelf never covers a wheel, and `reframe_overlay` reads its rect back and, while a DPI change on the way (tao rescales the window in its `WM_DPICHANGED` handler) left it off the display's frame, sets the frame again, at most three times, logging the final rect in physical pixels (a warning if it's still off). On macOS, `grape_platform::macos::frame_and_show` sets the frame in points and calls `orderFrontRegardless` in one main-thread call, which orders the window front although Grape isn't the active app. `focusable: false` keeps it from becoming key. The toast sits one window level below the overlay (D18).
- **Drag events come from the overlay's drop target.** On Windows that's Grape's own `IDropTarget`, sending `grape_platform::DropEvent` in global physical pixels (`DECISIONS.md` D13). On macOS it's wry's own handler, reported as Tauri's `WindowEvent::DragDrop`: wry accepts the drag as a copy, and the app adds the overlay's frame to its window-relative points to make the same `DropEvent`s (D18). The events:
  - `Enter { paths, … }`: **this is where the overlay learns which files are being dragged** on both OSes. Feed `paths` to `grape-core` to build the wheel. No paths means it isn't a file drag: close the wheel.
  - `Over { … }`: hit test → highlight.
  - `Drop { paths, … }`: hit test → run or cancel.
  - `Leave`: the cursor left the display. Keep the wheel and wait. On macOS, a `Leave` while the button is still down with the cursor still on the wheel's display is how Esc shows up (Grape can't read keys without permission), so the controller closes the wheel if no `Enter` or `Over` follows within 200 ms, and a button-up within 50 ms of the `Leave` counts as a refused drop (D18).
- The UI events (`wheel://open|highlight|close`, `toast://show|hide`) and their JSON are specified in `docs/design/m1-drag-wheel.md` §C; both sides test against the same golden fixtures. The shelf has two more, sent only to the `float` window: `float://view` (`{ items: [{ id, name, kind, missing }] }`, after every change and before every show) and `float://drag-ended` (`{ outcome }`: copied, linked, cancelled, nothing or failed), with the fixtures `float-view.json`, `float-view-empty.json` and `float-drag-ended.json` (D21). The panel has two, sent only to the `panel` window: `panel://open` (`{ seq, title, items: [{ id, name }], panel }`, before the window shows; also `panel_current`'s answer) and `panel://close` (`{ seq }`, after the window hid), with 10 fixtures: `panel-open-{compress,channels,normalize,merge}.json`, `panel-close.json`, and the command args `panel-run-{compress,channels,normalize,merge}.json` and `panel-cancel.json` (D31). The Shortcuts wheel adds one content kind and one close reason to the wheel's events, with the fixtures `wheel-open-shortcuts.json`, `wheel-open-shortcuts-empty.json` and `wheel-close-picked.json` (§C there points to `docs/design/m10-shortcuts-wheel.md` §6). Its Settings section has 16 more, which `events.test.ts` leaves out of its own list as it does `settings-view-*`: the view `shortcuts-view-macos.json` and `shortcuts-view-windows.json`, and one `shortcuts-step-*.json` per shape of a step edit (`keys`, `keys-unset`, `type-text`, `clipboard`, `open-url`, `apple-shortcut`, `apple-script`, `shell`, `keyboard-maestro`, `window`, `system`, `notify`, `speak`, `delay`), each read by Rust's tests and the page's. A drag wheel opens pending and fills in once `Enter` brings the paths; a Shortcuts wheel opens with its segments.
- During an OS drag the webview gets **no pointer events**. All highlighting is driven from `Over` positions sent to the UI. Don't rely on DOM `pointermove`. That's true of OS drags only. A Shortcuts wheel has no drag, so its page does get real pointer events, the first of Grape's overlay pages to. It still reads none of them: Rust polls the pointer (`PointerWatch`), runs the same hit test and sends the same `wheel://highlight`, and a click is the watch's `Down` and `Up`. The page only cancels `contextmenu`, `mousedown` and `dragstart`, so WebKit shows no menu and starts no selection or page drag, and it still calls nothing but `wheel_painted`.
- **Known risk (spike in M1):** `Enter` may not fire until the cursor moves after the overlay appears. Until it does, the wheel shows a neutral ring (M1: the numbered placeholder ring). macOS works the same way: Grape checks only the drag pasteboard's *types* and never reads its contents (see `PLATFORM_MACOS.md`), so the paths arrive with `Enter` there too.
- macOS full-screen Spaces may need a non-activating `NSPanel` for the overlay or the shelf. If a plain Tauri window can't float over full-screen apps, use the `tauri-nspanel` plugin and log it in DECISIONS.

## Threads and timing
- The platform monitor runs on its own thread (macOS: a polling thread; Windows: the hook thread *must* pump messages). It sends signals through a bounded channel.
- The controller runs on the Tauri async runtime. UI updates go out as Tauri events (`wheel://open`, `wheel://highlight`, `wheel://close`).
- Engines run on a worker pool (`tokio::task::spawn_blocking` or a dedicated `rayon` pool). Max concurrency = number of CPUs, and FFmpeg jobs = 2.
- Each file action runs on a "grape-action" thread of its own. On Windows, Share looks the files up there, in the multithreaded apartment. Then "grape-share" opens the sheet from its anchor window, and "grape-action" waits up to 30 s for the sheet to ask for the files. "grape-share" is a single-threaded apartment with a message loop, started on first use and kept for the app's life (D21).
- A drag out of the float shelf runs on the main thread, which owns the shelf window and OLE. On Windows it's a modal loop, so Tauri's other main-thread work waits until the drop or the cancel. A "grape-drag-watch" thread watches it and sends Esc after 3 s with no button down. On macOS the drag is AppKit's dragging session: the call returns at once and doesn't hold the main thread, the end comes from the source's callback, and there's no watchdog (D43). After the user moves the shelf, a "grape-float-snap" thread waits for it to be still and then snaps it on the main thread.
- While a tool panel is open on Windows, "grape-panel-esc" polls Esc every 30 ms and closes the panel on a press made with no mouse button down, until the panel's window first has the focus; after that Esc is the page's (D31). It stops when no panel is open.
- The Shortcuts wheel (D47, macOS for now) adds these:
  - The hot key handler runs on the **main thread**: Carbon calls it there. It reads the cursor, the mouse buttons and the app in front, sends one `HotkeySignal` without blocking, and returns. Binding a chord hops to the main thread and waits, so the main thread must never wait for the hot keys' lock: Pause rebinds on "grape-shortcuts-bind", and the exit only tries that lock.
  - "grape-pointer" is the pointer watch: parked while no Shortcuts wheel is open, and polling the cursor and the primary button every 8 ms while one is.
  - "grape-hotkey-forward" and "grape-pointer-forward" carry those signals to the controller's thread ("grape-wheel"), as "grape-signal-forward" does for drags. `Effect::Track` binds or lets go of Esc and Return and switches the watch on that thread, and returns only once the OS has done it.
  - "grape-shortcut" runs one picked shortcut's steps, one run at a time, and ends with `Input::RunEnded` on a waiting send, also when a step panics. A step's program gets its script from "grape-shortcut-stdin", so a long script can't hold the run past its limit.
  - "grape-shortcuts-bind" binds the hot key again, or lets go of it, after Pause is toggled.
  - "grape-kill" is short-lived: 500 ms after a program's group was asked to end, it kills what's left.
- **Budget:** under 16 ms from modifier signal to `wheel://open`, and under 100 ms until the wheel is painted. The Shortcuts wheel is measured from the hot key against the same 100 ms.

## Settings (persisted)

Stored in `settings.json` in the app's data folder by `tauri-plugin-store` (D19). The app's `settings.rs` owns the model, and the Settings window changes it only through the `settings_*` commands.

| Key | Default | Notes |
|---|---|---|
| `keys.conversions` | Shift | `"shift"`, `"ctrl"`, `"alt"` or `"meta"`. The three keys are always different. Windows never offers `meta`. |
| `keys.tools` | Command / Ctrl | |
| `keys.actions` | Control / Alt | |
| `output.location` | `next_to_source` | or an absolute folder path |
| `output.fallback_dir` | `~/Downloads/Grape` | used when the destination isn't writable. Absent means the default. A chosen folder is used only while it exists. |
| `sounds` | on | the highlight tick |
| `haptics` | on (mac) | the trackpad tick, separate from `sounds` |
| `launch_at_login` | on | the user's choice. A release build turns it on at first launch, and on Windows registers it again when `true` is stored but an uninstall took the Run value (D19). |
| `terminal_app` | Terminal / Windows Terminal | `"terminal"` or `"iterm2"` on macOS, `"windows_terminal"` or `"powershell"` on Windows |
| `onboarding.done` | absent | `true` once the welcome card's "Got it" is clicked; until then Settings opens at launch (not at login) |
| `tools.compress` | `balanced` | `"small"`, `"balanced"` or `"high"`; the last Compress preset that ran |
| `tools.normalize_lufs` | `-16` | a whole number from −24 to −10; the last Normalize target that ran |
| `features.v2` | off | dev toggle until v2 ships |

**`shortcuts.json`** (D47) is a second file in the app's data folder (`BaseDirectory::AppData`, expected to be the folder `settings.json` is in; nobody has looked on a Mac yet), written by Grape itself and never through the store plugin, so a broken one never takes `settings.json` with it. It holds the Shortcuts wheel's switch, hotkey, where it opens, and the menus with their shortcuts and steps, in plain text. `shortcuts/store.rs` reads it once at launch and writes it after every change (a `.tmp` beside it, then a rename); a file it can't use is renamed `shortcuts.unreadable.json` and the defaults are used. Only the `shortcuts_*` commands change it. Its format, limits and loading rules are in `docs/design/m10-shortcuts-wheel.md` §7, and nowhere else. Where the wheel isn't built (Windows today) the file is never read, made or written.

## Error model
- Engines return `GrapeError { kind, user_message, detail }`. The toast shows `user_message`, and `detail` goes to the log file.
- Logs go to the app log dir via `tauri-plugin-log`, rotated. **Never log file contents**, only paths and sizes. For the Shortcuts wheel the rule is stricter: nothing the user typed or picked is logged, not a name, text, script, link, path or app id, and never a serde message, which can quote the file (D47).
