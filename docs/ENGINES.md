# Engines, codecs and licensing

## Licensing rules (Grape is free and open source; see DECISIONS D2)

1. **Grape's own binaries** (the Tauri app and our crates) may link only permissive code (MIT/Apache/BSD/ISC/Zlib) or LGPL libraries that are *dynamically* linked. CI checks the crates with cargo-deny against `deny.toml` (DECISIONS D23).
2. **GPL/AGPL tools may ship only as separate sidecar executables** that Grape runs as a child process. Never link them into our binary.
3. Every bundled third-party binary ships with its license text in `licenses/` and an entry in `THIRD_PARTY_NOTICES.md`. GPL sidecars also need the exact source version and a link to the source (or a source archive on the GitHub Release). `THIRD_PARTY_NOTICES.md` is generated, so the entry goes in its template, `about.hbs`. `licenses/README.md` has the steps.
4. Record every new library or sidecar in `DECISIONS.md`: name, version, license and why it's needed.
5. Skip anything with *restrictive non-OSS* terms, like the `unrar` freeware license. Use libarchive (BSD) for RAR reading instead, through Grape's own bsdtar build (D27).

## FFmpeg build

- **Grape builds its own FFmpeg 9.0.2** (DECISIONS D24): `scripts/ffmpeg/build.sh <target>` builds `ffmpeg` and `ffprobe` from the source tarballs pinned in `scripts/ffmpeg/sources.json`, with only what Grape uses. `scripts/ffmpeg/README.md` says how to run it and what each OS needs.
  - Windows x64: cross-compiled on Linux with mingw-w64 (win32 threads), fully static. `ffmpeg.exe` and `ffprobe.exe` import only Windows' own DLLs (`KERNEL32`, `SHELL32`, `bcrypt`, `msvcrt`). About 28 MB each, against BtbN's 165 MB.
  - macOS: built natively on an Apple silicon and an Intel Mac, for macOS 11.0 or later, then joined with `lipo` into one universal file and signed (D25).
  - Linux x64: only for the `engines-it` tests. About 28 MB each.
  - Each build also writes `BUILDINFO.txt` and `grape-ffmpeg-sources.tar`, the corresponding source: every tarball as downloaded, the script and `licenses/ffmpeg/`. The tar and both builds, zipped (`grape-ffmpeg-windows-x64.zip`, `grape-ffmpeg-macos-universal.zip`, D45), go on every draft release (below).
  - **CI:** `.github/workflows/ffmpeg.yml`, a reusable workflow that `release.yml` calls once for everything (without cache) and `ci.yml` twice, so that the Windows installer never waits for a Mac job: `targets: windows`, then `targets: macos` with the first call's `windows-sources` (the uploaded bundle's hashes). One job per target: `windows-x86_64` on `ubuntu-24.04` (exactly that image: its mingw-w64 11.0.1 and GCC 13.2.0 are the runtimes `licenses/ffmpeg/` describes, and the job checks both), `macos-arm64` on `macos-latest` and `macos-x86_64` on the Intel image (`macos-15-intel`). Each caches `dist/` on the hash of `scripts/ffmpeg/**` and `licenses/ffmpeg/**` (a hit skips the build) and the tarballs on `sources.json`, for `GRAPE_FFMPEG_TARBALLS`, and uploads `build.sh`'s logs (`notices-found.json` among them). `windows-check` runs the exes on Windows: the gate's checks, the protocols, the configure line and an MP4. `merge` joins the Mac halves with `lipo`, signs them ad hoc, checks each half's minimum macOS against Grape's and that it links only the OS's libraries, and runs the gate's checks, the protocols, the configure line and an MP4 on each half the runner can run. `sources` compares the three targets' source bundles (byte for byte when they're from one commit, else by their contents) and the one uploaded. That one comes from `windows-x86_64` alone, uploaded before its exes; the Mac jobs start after it, and `merge` only after `sources`, so no run holds FFmpeg's programs without their source. The Mac halves travel to `merge` as artifacts kept 7 days, so a failed `merge` can be re-run the next day. The artifacts: `ffmpeg-x86_64-pc-windows-msvc` and `ffmpeg-apple-darwin` (Tauri's names, the per-arch Mac files too, with `BUILDINFO`, `SHA256SUMS` and `licenses/ffmpeg/`), and `ffmpeg-source`, which `release.yml` attaches to the draft, with the other two zipped (D45).
- **Until it points at a published release's copies (lane B, M7), `scripts/sidecars.lock` pins prebuilt builds for local testing only** (D22, D25): BtbN's win64 GPL build and martin-riedl.de's for macOS. They never ship: they're GPL-3.0 with GPL-2.0-only libzvbi code in them, and link about 100 libraries. `scripts/fetch-sidecars.ps1` (Windows) and `scripts/fetch-sidecars.sh` (macOS) download and check them into `apps/desktop/src-tauri/binaries/` (`PLATFORM_WINDOWS.md` and `PLATFORM_MACOS.md` → "Sidecars"). Change a pin in the lock, never in the scripts. What every installer and DMG carries is Grape's own build, which CI builds with `build.sh` in the same run (2026-10-26, #27), through D25's gate; the lock points at Grape's release only at M7.
- **What's in it.** `--disable-everything` and `--disable-autodetect`, then only:
  - **GPL-2.0-or-later:** `--enable-gpl` for `libx264`; never `--enable-version3` (nothing needs it) or `--enable-nonfree` (can't be redistributed).
  - **Libraries:** `libx264` (8-bit), `libmp3lame`, `libopus`, `libvorbis` (with libogg), `libvpx` (the VP9 encoder only), `libdav1d` (AV1 decoding) and `zlib`, all static.
  - **Encoders:** `libx264`, `libmp3lame`, `libopus`, `libvorbis` and `libvpx-vp9`, plus FFmpeg's own `aac`, `flac`, `pcm_s16le`/`s24le`/`s16be`/`s24be`, `mpeg4` (with `h263`, which it's built on), `wmv2`, `wmav2`, `gif` and `png`, and for the tools (D26) `alac` and `pcm_s32le`/`f32le`, so Normalize Volume and Audio Channels keep ALAC, 32-bit and float WAV. Nothing else.
  - **Decoders, parsers and bitstream filters:** all of FFmpeg's, because people drop every kind of file and stream copies need the bitstream filters. The libraries' Opus, Vorbis and VPx decoders are left out; FFmpeg's own are picked first anyway.
  - **Demuxers:** the ten in `-format_whitelist` plus `image_png_pipe` (the GIF palette). **Muxers:** the fourteen of the fifteen targets (WMV and WMA share `asf`) plus `image2pipe`, and `null` for the tools' measuring passes (D26; it opens no file).
  - **Filters:** the ones Grape passes (`scale fps palettegen paletteuse aformat pan`, and `ebur128 volume alimiter` for Normalize Volume, D26), the ones ffmpeg inserts itself (`format aresample premultiply_dynamic null anull transpose hflip vflip rotate crop`, and `trim atrim` for an input's `-ss`), and `sine testsrc` with the `lavfi` input device, which only the engine tests use to make their sources.
  - **Protocols:** `file` and `pipe`, and `--disable-network`: there's no network code in the binary at all (golden rule 3).
  - Hardware encoders are for a later slice. Media Foundation (`--enable-mediafoundation`, Windows) and VideoToolbox (`--enable-videotoolbox`, macOS) are OS frameworks and add no library; NVENC, AMF and oneVPL (`--enable-nvenc --enable-amf --enable-libvpl`) would each add MIT headers or a dispatcher, and a notice.
  - `build.sh` checks the component lists configure generates against these, exactly, and on Windows that the exe imports only Windows' own DLLs. The `engines-it` test `the_sidecar_has_everything_grape_uses_and_is_redistributable` checks the encoders, muxers, filters and demuxers of whatever FFmpeg it's given, and the engine tests make their sources only with what this build has.
- **Licenses:** `licenses/ffmpeg/` has the GPLv2 and each library's text, `ffmpeg-notices.txt` every license notice inside the sources the build compiles and every other statement about a license there, each with what it means for Grape (`build.sh` checks it on every build), the license texts of code FFmpeg and libvpx took from dsd2pcm, Aaron D. Gifford's SHA-2, Glumpy and libwebp, `SOURCE.md` the configure line and the pins, and `about.hbs` the notices entry (rule 3).
- Ship as a Tauri sidecar via `bundle.externalBin` with target-triple suffixes (`ffmpeg-x86_64-pc-windows-msvc.exe`, `ffmpeg-universal-apple-darwin`, …), plus `ffprobe`. The app finds them next to its own executable and passes them in `SidecarPaths`; the engine never looks on `PATH`.

### How Grape runs FFmpeg (`grape-engines/src/media/`)

- **Offline and contained.** `ffprobe` and `ffmpeg` both get `-protocol_whitelist file` and `-format_whitelist mov,matroska,avi,asf,mp3,flac,ogg,wav,aiff,gif`, and every path is a `file:` URL. So no source can reach the network or open other files: an HLS, DASH or `ffconcat` playlist renamed `.mp4` is refused before it reads anything, and no file name is ever taken for an option or a protocol (`pipe:1.ogg`, `-v error.wav`). On Windows, a source or output folder whose path isn't valid Unicode (an unpaired surrogate, which NTFS allows) is refused before FFmpeg runs: FFmpeg rebuilds its argv as UTF-8, would turn it into U+FFFD and open or write another file.
- **Probe first.** `ffprobe -of flat` gives the container, the duration, and for the first video stream that isn't cover art (`0:V:0`) and the first audio stream (`0:a:0`) their codec, size, pixel format, rotation, rate, channels, the audio's channel layout (or that it has none) and bit depth, and whether any video stream has B-frames; and for the tools (D26) every stream by its index (its kind, codec and tag, whether it's cover art, bitrate, the audio's channels, rate, depth and sample format, the video's transfer function and frame rate, and how many frames it holds where the container says: MP4 and MOV do, Matroska doesn't) and the container's bitrate. This probe never reads tags; the tools' tags probe reads tag keys (Tools below). A source without the stream the target needs is refused before anything is written, and before the job waits for an FFmpeg slot ("… has no sound to save as MP3", "… has no video to convert"); so is one too long for AIFF (its row below).
- **Only what the user sees.** The output keeps that video and that audio stream. Subtitles, data streams, further audio tracks and cover art are dropped. MP4 and MOV also get `-write_tmcd 0`: their muxer would otherwise rebuild a camera's timecode (GoPro, DJI, pro cameras) as a data track of its own.
- **Writing:** into a temp file next to the planned name (`-y` is safe: the temp name is new), with the output format forced by `-f`; the planned name never appears in the argv. Then the output is checked: not empty, within AIFF's 4 GiB for AIFF, and with the target's stream by `ffprobe`; the file is synced (reopened for writing: Windows only flushes a writable handle), and it's published no-clobber like every engine's.
- **Progress** comes from `-progress pipe:1`'s `out_time_us` against the source's duration (an output time past it counts as the end; with no duration the bar moves only at the end of each pass). FFmpeg's passes fill the bar to 98 % by their weights, the output check and sync take it to 99 %, and it reaches 100 % only once the file is published. A run that copies streams fills only half of the 98 %, so a re-encode after a refused copy, even one refused at its last step, always has the other half; a copy that works is fast, and the bar goes from 49 % to the check. It never moves backwards. The GIF palette pass (30 % of a GIF's bar, the GIF pass 70 %) reports nothing until it ends, because FFmpeg prints no output time before the palette's only frame. **Cancel** kills the child within about 50 ms and waits for it, then the temp files go; every other way out of a run (an error, a timeout, a panic in the progress callback) kills and waits for it too. At most **two FFmpeg jobs** run at once; a job that waited for its turn checks again that its source is still there ("Grape couldn't read …" if not).
- **Process hygiene:** absolute program paths only, stdin empty, `FFREPORT` removed, and on Windows `DETACHED_PROCESS | BELOW_NORMAL_PRIORITY_CLASS` (no console at all, so no window flashes and Windows starts no console host, `conhost.exe`, beside it, as for `grape-heif.exe`; encoding doesn't starve the desktop). On Windows each run also goes into the app's Job Object right after it starts (D22, through D33's hook): it ends with Grape however Grape ends, holds one process, shows no error dialog, and has no memory cap. A run that can't be put in one runs on uncontained (it fails open, unlike the helpers), and the reason goes in the job's log detail. `ffprobe` has 60 s.
- **Errors:** a source FFmpeg can't read, or one the whitelist refuses, or one `ffprobe` can't finish within its 60 s → "… isn't a readable MP4 video"; a sidecar that won't start → "Grape's media converter is missing. Reinstall Grape."; an `ffmpeg` whose output pipes fail → couldn't write the format; FFmpeg's own failures are judged by the end of its stderr: "Error opening input" with "No such file or directory", "Permission denied" or "Input/output error" (the source was moved, deleted or its drive went away) → "Grape couldn't read …"; "No space left", "Disk full", "Read-only file system", "Permission denied", "Input/output error" or "No such file or directory" (the output folder went away) → couldn't save; "Invalid data found" → not readable; anything else, a muxer refusing a copied stream included → couldn't write the format. An output gone by the time it's checked (its folder was removed while FFmpeg wrote into it) → couldn't save.

More channels are downmixed to 7.1 from the layout FFmpeg guesses, which FFmpeg 9.0.2 has for 10, 12, 14, 16 and 24 channels (6.1 not for 14); other counts fail (Known limits). libopus's default mapping puts the channels of 5.0 and 6.1 in the wrong speakers (5.0: the centre and the back pair; 6.1: the centre, the back centre and the left side), so 3 to 8 channels get its surround mapping (`-mapping_family 1`), which places every Vorbis layout right but codes the fourth channel of 5.1, 6.1 and 7.1 as the LFE, keeping nothing above about 400 Hz there. Without a layout that channel is a track: 7 channels go to 7.1 with the LFE silent (8 channels out, `pan=7.1\|c0=c0\|c1=c1\|c2=c2\|c4=c3…`), and 6 and 8 channels, and more downmixed to 7.1, keep the default mapping, which places them right at full bandwidth. 2.1, the only standard layout of 3 or more channels FFmpeg remixes to fewer, becomes stereo, which, like mono, keeps the default mapping |
| aiff | — | `pcm_s16be` or `pcm_s24be`, as wav | AIFF's sizes are 32-bit and FFmpeg wraps them past 4 GiB, so a source whose duration says the samples won't fit (24-bit stereo 48 kHz past about 4 h 8 min) is refused before anything is written ("… is too long to save as AIFF."), and an output past the limit fails its check |
| wma | — | `wmav2 -b:a 192k`, with wmv's limits | |

Video from an AVI or WMV (ASF) source is never copied: those containers keep only decode times, so copied B-frames would play out of order, and FFmpeg writes that without an error. Their audio follows the rules above.

A copied conversion that FFmpeg rejects (a stream can fit by its codec and still not mux) is retried once, re-encoding everything, filling the other half of the passes' share of the bar (Progress above). Only FFmpeg's own refusal is retried: a failed exit judged "not readable" or "couldn't write the format" (Errors above). A write failure (disk full, no permission, a read-only drive, the folder gone) is reported at once as "couldn't save", a source FFmpeg can no longer open as "couldn't read", and a sidecar that won't start or whose pipes fail, or a cancelled job, is never retried. A retry of those would cost a whole encode for nothing, or quietly publish a re-encode where a copy was due.

**Known limits** (later slices): only the first audio track is kept; the GIF palette pass shows no progress of its own; HDR or 10-bit video comes out washed out in yuv420p without tone mapping; audio without a channel layout and more than 8 channels converts to OPUS, OGG or WebM only when FFmpeg has a layout to guess for that count (10, 12, 14, 16 or 24 channels in 9.0.2; 14 not in 6.1), and otherwise fails as "couldn't write"; at 128 kb/s libopus codes the two channels of each coupled pair (front, side, back) of 5 or more channels partly together above about 4–6 kHz, so a high tone in one of them shows in the other at −3 to −16 dB (its intensity stereo; below that, and between pairs, they stay apart by 39 dB or more); a layout FFmpeg names only by its channels (not a standard one) that it remixes to stereo, such as the front pair with height channels, still gets `-mapping_family 1`, a valid stereo Opus with a family-1 header; a WMV3 or VC-1 WMV with B-frames, a few seconds long, can still now and then end its GIF early on 9.0 by the GIF frames its last frame covers (its packets have no duration, and it isn't read again; 100 runs of a 720×480 sample under load all came out whole); a WMV of a single frame whose picture starts after its sound makes no GIF (the palette pass gets no frame, so "couldn't write a GIF file"), on 6.1 and 9.0 alike; GIFs over 30 s aren't warned about; hardware encoders (Media Foundation, NVENC, AMF, QSV, VideoToolbox) aren't used yet; when Grape dies mid-job (a crash, End task, Force Quit), the partial `.grape-tmp-…` output (and a GIF's palette file) stays next to the original on every OS, and on macOS (and Linux) FFmpeg, which no job object ends there, encodes on to the end and leaves the whole output under its temp name (D22's Known limits has the test); on Windows its Job Object ends it with Grape.

## Tools (D26)

Lane B's five v1 tools (DECISIONS D26). They land one tool and format at a time: until a pair's commit is in, `run_job` refuses it and the app says "… is coming" (D35). In so far, every FFmpeg one: Remove Audio on MP4, MOV and MKV; Remove Metadata and Compress on MP3, M4A, WAV, FLAC, MP4, MOV and MKV; Audio Channels and Normalize Volume on MP3, M4A, WAV and FLAC. Of the image ones: Remove Metadata on JPG, PNG, WebP and GIF, and Compress on JPG and PNG. That's all of D26's v1 slice. They run FFmpeg as "How Grape runs FFmpeg" says (the whitelists, `file:` URLs, a temp file, the output check, the no-clobber publish, at most two jobs at once), with these differences:

- **Every track stays** except what the tool removes. Streams are mapped by their index (`-map 0:<i>`, never `0:V` or `0:a`), so subtitles, further audio tracks, chapters, cover art and MKV attachments come along. Conversions keep only what the user sees (above). Two exceptions: the audio tools (Normalize, Channels, Compress on audio) write the first audio track only, so an M4A with a second one keeps its first; and Compress and Remove Audio keep a video's cover art only in an MP4 without an iPhone's keys. FFmpeg's MP4 and MOV muxer writes cover art only into iTunes-style metadata (`covr`), which a MOV never gets and an MP4 with the keys gets in its place (`use_metadata_tags`, below), and it can copy an MKV's cover art (an image attachment) back only as a one-frame video track (6.1 and 9.0.2 alike); so in a MOV, an MKV or an MP4 with the keys it's left out, and lost. Their output check counts cover art too: cover art they kept that the muxer didn't write fails the job.
- **Only Remove Metadata removes metadata.** The other tools keep tags, `creation_time` (FFmpeg's CLI drops it from every remux, `ffmpeg_mux_init.c:3034`, so it's set again from the source), iPhone `com.apple.quicktime.*` keys (`-movflags +use_metadata_tags` with the brands blanked, on MP4 and MOV only, never M4A), cover art, chapters, ICC and EXIF/XMP/IPTC. Normalize and Channels remove only ReplayGain, R128 and `iTunNORM`, which their change makes wrong. A Broadcast Wave's `bext` chunk (a recorder's time reference, UMID and coding history) is written again (`-write_bext 1`) when the source had one. What FFmpeg's muxers can't write back is lost by every tool that re-muxes: iTunes freeform (`----`) atoms, some ID3 frames (UFID, POPM, WXXX), WAV cue points.
- **Nothing to change, nothing written.** A job that would change nothing fails with `ErrorKind::NoChange` and says why ("… is already mono.", "… has no sound to remove.", "… is already compact. Try Small."). Every such check runs before anything is created, except Compress's size rule, which runs after the encode. Normalize's come from its measuring pass, which writes nothing (the `null` muxer opens no file), and its temp file is made only after it and its check passes.
- **The tags probe.** Every media tool also runs `ffprobe -show_entries format_tags:stream=index,codec_type,codec_tag_string:stream_tags:stream_disposition=attached_pic:chapter=id -of flat` (with `-export_xmp 1` for the MOV family). Normalize and Channels need it too, for `creation_time`, which FFmpeg drops from an M4A as from any file it writes. Grape keeps only the tag *keys*; the only values it keeps are a track's language (`[a-z]{2,3}`, not `und`), `creation_time` (an ISO 8601 date) and a stream's MIME type (a font's, an image's, or other): an attachment's, or a video track's that a copy made of an MKV image attachment (Remove Metadata, Metadata removal below). It's read line by line as `ffprobe` prints it, keeping nothing else, so a large tag (an editor's XMP history) costs only reading time; a value too long to read whole (over 4 KiB) is judged by its key. Output past 64 MiB stops the probe and isn't an error: what it printed before counts, and "other fields" stands for the rest.
- **Same quality** for Normalize and Channels: MP3 → LAME VBR picked from the source's bitrate per channel (≥112k V0, ≥80k V2, ≥56k V4, else V6); AAC → AAC at the source's bitrate per channel (64k–160k, rounded up to 8k; at most 512k in all); ALAC → ALAC; WAV → the same PCM (`pcm_s16le`, `s24le`, `s32le` or `f32le`); FLAC → FLAC level 8 with exact Rice parameters at 16 or 24 bits. 16-bit outputs get TPDF dither (`aresample=osf=s16:dither_method=triangular`); the sample rate is always kept. A 32-bit ALAC or FLAC source is refused ("… is a 32-bit recording. ALAC would cut it, so nothing was saved."): FFmpeg's `alac` encoder writes at most 24 bits, and `flac` too outside its experimental mode, so its last 8 bits would be lost.

**Compress, the rules around the table:**
- AAC's per-channel rates are capped at 512k in all, and AAC is written at 48 kHz at most (88.2 and 176.4 kHz to 44.1, other rates over 48 kHz to 48): FFmpeg's encoder takes at most 96 kHz, and these bitrates have nothing to spend above 24 kHz. In a video, an audio track is copied when it's AAC with a known bitrate within 1.1 × the target.
- A source that's already small enough ends `NoChange` before encoding: an MP3 whose average bitrate (the stream's, or else the file's) is within 1.1 × the preset's nominal one (half of it for mono), an AAC M4A within 1.1 × its target, a JPEG that isn't resized and whose estimated quality (from its DQT) is at most the preset's + 3.
- FLAC is always `-compression_level 8 -exact_rice_parameters 1` (levels 11 and 12 leave the streamable subset). Rates of 88.2, 176.4 and 352.8 kHz go to 44.1, 96, 192 and 384 kHz to 48. A source deeper than 24 bits, or float, is refused ("… is a 32-bit recording. FLAC would clip or cut it, so nothing was saved."): FLAC would clip it or cut bits. So is one of more than 8 channels, FLAC's most. The 95 % rule holds at High or when nothing was reduced, 90 % when the depth or rate was.
- Video: the first video that isn't cover art is encoded (and not a still-image track either when there's real video: a cover FFmpeg copied into an MKV comes back as a one-frame PNG or JPEG video track) (`-preset medium -profile high -pix_fmt yuv420p`, Lanczos, never scaled up, both sides even; the scale works on the displayed size, so a rotated source comes out upright). Every audio track, cover art (in an MP4 without an iPhone's keys, above), MP4/MOV `mov_text` and MKV subtitles and attachments are kept, the tags and chapters too; MP4/MOV timecode is written again from its tag; further videos and data tracks are dropped. A file with neither picture nor sound is refused ("… has no sound or video in it."); one with sound only (an audio-only MP4) gets only its audio compressed. Small caps an average rate over 31 fps at 30 (`r/⌈r/30⌉`: 60 → 30, 50 → 25, 120 → 30). HLG (`arib-std-b67`, iPhone Dolby Vision 8.4 included) becomes 8-bit H.264 with its BT.2020 and HLG tags, as conversions do; PQ (`smpte2084`, HDR10) is refused ("… is HDR10 video, which Compress can't keep yet."). If the muxer refuses a copied audio track, the job retries once re-encoding every audio track. Opus of 3 to 8 channels without a layout (channel mapping family 255, which says its channels aren't speakers), in a video or an M4A, keeps each channel to itself: FFmpeg's guess for it has an LFE for 3, 6, 7 and 8 (2.1, 5.1, 6.1, 7.1), which AAC codes band-limited, wiping that channel, so it gets `pan=<layout>|c0=c0|c1=c1…` (`-filter:<o>` in a video) with a layout of its count that has none: AAC's own 3.0, 4.0 and 5.0, and for 6 to 8, which AAC has no configuration for without an LFE, hexagonal, 7.0 and octagonal, which FFmpeg's encoder writes with a program config element (6.0 would come back as hexagonal, its back centre last). 9.0.2's output of each reads back in the same order in 6.1.1 and 9.0.2; 6.1.1's encoder writes the last three so that both read them back as unknown layouts. Such Opus of 1 or 2 channels gets `pan=mono` or `pan=stereo` the same way: the Opus decoder hands it over with no layout, which AAC refuses. Every other track without a layout is read the way players read it, as the standard layout for its count (Known limits).
- JPEG: decoded without applying the orientation, so the pixels stay as stored and the EXIF (Orientation included) is carried; PixelXDimension and PixelYDimension follow a resize; the JFIF pixel density, ICC, XMP, IPTC and comments are carried, the segments after the encoder's own JFIF, EXIF and ICC ones. Gray stays gray. A picture over twice the long side is first averaged down by a whole factor (Grape's own loop, which a cancel stops at the next row), then Lanczos3 takes it the rest of the way; what decoding, scaling and encoding hold is checked against D16's 1 GiB before any pixel is decoded, and the encode stops at its next write after a cancel. (Lanczos3 itself can't be stopped, but it works on at most twice the long side.) The estimated quality is libjpeg's scaling read backwards from the luminance table's sum. CMYK and YCCK JPEGs are refused ("… is a print (CMYK) JPEG, which Compress can't keep yet."). A source with data after its end (gain maps, motion photos, MPF) loses it, and its XMP, which describes it. "Try Small" is said when Small would scale it, or when it's 4:4:4 or gray and its quality is over 73: a subsampled (4:2:0) JPEG Small wouldn't scale rarely comes out smaller at 4:4:4.
- PNG: exact reductions only (16 → 8 bits when every sample allows it, no alpha when it's all opaque, gray, gray at 1, 2 or 4 bits when every level is one of that depth's, an exact palette of up to 256 colors at 1, 2, 4 or 8 bits an index, its transparent colors first so `tRNS` is short (not for opaque gray, which stays gray: a palette of its few levels came out bigger about as often as smaller, on small icons and noisy scans); gray from color and palette not with an ICC profile, cICP, mDCV or cLLI), then `png`'s High compression with adaptive filtering, not interlaced. The pixels are read 65,536 at a time, never copied whole (the peak is the image and its packed form, then the packed form, the PNG and three of its rows while it's written; D16's limit checked before decoding), and a cancel stops the reduction within a span and the write within 32 KiB of it. The encoder compresses a row once it's whole, so a step runs on to the end of its row: noisy rows of tens of KB (8,000 to 20,000 pixels wide) can answer a cancel 50 to 70 ms late, and rows of many megabytes (millions of pixels wide) only after the row. Carried: the ICC profile (its name becomes `_`; kept rather than sRGB when a source has both, as PNG 3 ranks them), sRGB, gAMA, cHRM, cICP, mDCV, cLLI, `eXIf`, the text chunks (those after the image data stay after it), pHYs and tIME; dropped: sBIT, bKGD, hIST, sPLT, `iDOT` and unknown chunks. Animated PNGs are refused ("… is animated. Compress works on still PNGs for now."). As with Remove Metadata, the content decides: a PNG named `.jpg` is compressed as a PNG.
- "Try Small" is said only when Small would do more: for lossy formats unless Small would skip or copy it too (a video with no picture whose every audio track is AAC within Small's bitrate); for FLAC and WAV when the source is over 16 bits, or over 48 kHz at High; for JPEG when Small would scale it, or it's 4:4:4 or gray and its quality is over 73; never for PNG.

**Normalize Volume** measures with `ebur128=peak=true` (mono as dual mono, so a mono file plays as loud as stereo at the same target), into the `null` muxer (output `-`, nothing written), and reads the last summary's integrated loudness `I` and true peak `TP` (a summary starts a line `[Parsed_ebur128…`, which no tag in the input dump above it can print; a failed measure's log detail leaves out its stderr, which repeats the tags). With `G` = target − `I`: no summary or `I` ≤ −70 LUFS is "too short or too quiet to measure" (`NoChange`); |`G`| ≤ 0.5 LU with `TP` under the ceiling is "… is already at −16 LUFS." (the target asked; `NoChange`); `TP + G` under the ceiling writes with a linear `volume` gain (double precision); otherwise the gain goes through `alimiter` at the ceiling −0.5 dB, oversampled 4× up to 48 kHz and 2× up to 96 kHz, measured again and corrected by what it fell short (at most two checks; it stops within 0.3 LU). Each file is normalized on its own (track gain).

**Audio Channels:** stereo → mono `pan=mono|c0=0.5*c0+0.5*c1`; mono → stereo `pan=stereo|c0=c0|c1=c0`; 3 or more channels with a layout `aresample=ochl=<mono or stereo>:rematrix_maxval=1` (5.1 → stereo: FL 0.414, FC 0.293, SL 0.293, no LFE; it can't clip, on every codec); 3 or more without a layout average to mono and are refused for stereo (ambisonics and polyphonic recorder WAVs have no left and right). Each mixes in double precision (`aformat=sample_fmts=dbl` first): `pan` and swresample would otherwise mix 16-bit audio in 16 bits, rounding without the TPDF dither that follows.

**Known limits:** camera telemetry tracks (GoPro GPMF, DJI, Apple `mebx`) are dropped by Compress and Remove Audio, since FFmpeg can't write them back; Compress keeps only the first video stream that isn't cover art; it encodes x264 only, so an HEVC source at High can end `NoChange`; it loses a JPEG's gain map or motion-photo video; user data inside the H.264 or HEVC bitstream (SEI) stays even through Remove Metadata; FFmpeg (6.1 and 9.0.2 alike) writes the source's ReplayGain into a new MP3's Xing/LAME header from what it decoded, so a player that reads it there, rather than in the ID3 tags Normalize and Channels blank, applies the old gain; there's no album gain; Matroska rarely says a track's bitrate, so an MKV's AAC is re-encoded rather than copied; an audio track AAC can't hold (more than 8 channels, or a layout such as 5.1.2 or 7.1.4) fails Compress on a video: FFmpeg's AAC encoder refuses it; an audio track of 3 to 8 channels without a layout that isn't Opus (a WAV without a channel mask, PCM in an MKV, which stores no layout for PCM) is read as the standard layout for its count (FFmpeg's guess: 2.1, 4.0, 5.0, 5.1, 6.1, 7.1), as players read it, so a Blu-ray rip's 5.1 PCM stays 5.1, but where the channel that layout calls the LFE (the 3rd of 3, the 4th of 6 to 8) isn't one, as in a field recorder's polyphonic WAV, Compress's AAC keeps only its lows, and its FLAC of such a WAV is labelled with that layout; Normalize reads such a WAV the same way: `ebur128` weighs that channel as the LFE, at 0, so sound only there measures as silence ("… is too short or too quiet to measure its loudness."), and the WAV it writes has FFmpeg's guessed channel mask; Normalize on Opus without a layout (mapping family 255) in an M4A fails as "couldn't write" (FFmpeg's AAC encoder refuses its layout, and 6.1.1 can't measure it); Small's frame-rate cap leaves out an MP4 or MOV camera timecode (`-write_tmcd 0`), whose frame number would be read at the new rate; a VBR MP3 without a Xing header is judged by its first frames' bitrate; a lossy Normalize output can sit a little over its ceiling (the encoder's own overshoot), and Normalize on it again then works again rather than ending `NoChange`; Remove Metadata keeps an ASS/SSA subtitle's `[Script Info]` (its title and authors) without reporting it, and an MKV font's own tags; WebP, TIFF and HEIC Compress and TIFF and HEIC Remove Metadata are coming (D28).

## bsdtar build

Grape reads RAR with libarchive's `bsdtar`, built by Grape (D27). Not the OS's bsdtar (too old on Windows 10 and macOS 13–15.3, and neither decodes filtered RAR4), and not libarchive linked into Grape (a crash in the C decoder must end only bsdtar).

- **Source and patches:** `scripts/bsdtar/sources.json` pins libarchive 3.8.10's release tarball (URL, SHA-256, size) and the six patches in `scripts/bsdtar/patches/`, in order, each with its SHA-256: three upstream fixes (the NULL-name guard, Windows name conversions, the RAR4 symlink bound) and three of Grape's (a UTF-8 code page in the Windows manifest, `@archive` reading only RAR and RAR5, the version marker). **Change the pin in `sources.json`, never in the scripts**, and bump the marker with every change to the series.
- **Build scripts:** `scripts/bsdtar/build.ps1` (Windows x64, MSVC, static CRT) and `build.sh` (macOS arm64 + x86_64, minimum macOS 13.0, merged with `lipo` and signed ad hoc; Linux for local tests). Every optional library is off, so bsdtar links nothing but the OS: KERNEL32, ADVAPI32 and bcrypt on Windows, libSystem on macOS. `-Install` / `--install` copies the result into `apps/desktop/src-tauri/binaries/` for `tauri dev`. `licenses/libarchive/SOURCE.md` has the exact CMake lines.
- **The version line** is exactly `bsdtar 3.8.10-grape.1 - libarchive 3.8.10 libb2/bundled ` (macOS adds `CommonCrypto/system` before `libb2/bundled`). The build checks it exactly; the bundling gate (`scripts/check-sidecars.mjs`) checks the `-grape` marker, `licenses/libarchive/` and a `## libarchive` section in the notices.
- **CI:** `.github/workflows/bsdtar.yml`, a reusable workflow that `release.yml` calls once and `ci.yml` once per OS (`targets: windows`, `targets: macos`), so each bundle waits only for its own. It builds per OS, checks the imports, the manifest or architectures, the version line and the copyright lines of the compiled sources, and runs `scripts/bsdtar/smoke.py`, a smoke test in Grape's exact environment on libarchive's own RAR test files. It's cached by the hash of `scripts/bsdtar/` and `licenses/libarchive/copyright-lines.txt` (a cache hit skips the copyright check, so a change to the file must miss) and uploads the binaries as artifacts for the same run. CI's `rar-it` jobs run the engine's RAR tests against them. No GitHub Release until M7, and `scripts/sidecars.lock` has no bsdtar.
- **Shipping:** a sidecar in the per-OS sidecars overlays' `externalBin` (`tauri.sidecars.windows.conf.json`, `tauri.sidecars.macos.conf.json`), next to FFmpeg, with `licenses/libarchive/`. Every installer and DMG carries it, from the same run's `bsdtar` workflow (D27, #27).
- **How Grape runs it** (`grape-engines` `archive/rar/`): only as `bsdtar -c -P -f - --format pax @-`, with the RAR written into a stdin pipe (never a file handle), in a new, empty, private folder, with only `PATH` (that folder), `TZ=UTC0`, `TAR_READER_OPTIONS=rar:hdrcharset=UTF-8`, plus `SystemRoot` (Windows) or `LC_ALL=en_US.UTF-8` (macOS), and `CREATE_NO_WINDOW` on Windows. A Rust preflight of the RAR's headers runs first. The output counts only with exit 0, an empty stderr, a tar end marker followed only by zeros, and entries matching the RAR's headers one to one by kind, size and CRC32. A 60 s stall watchdog, no total time cap.

## HEIC and AVIF build

Grape converts HEIC and AVIF in one helper process on both OSes (D33, D41): a crash or a hang in a HEIF or AV1 decoder must end only the helper, and neither libheif, dav1d, ImageIO nor an AV1 frame encode can be cancelled partway through. The engine side is `grape-engines`' `heif.rs` and `helper.rs`; both helpers speak `crates/grape-heif-proto`, protocol 2: an encode names its format (`heic` or `avif`), the probe answers per format, and the `ftyp` sniff tells HEIC from AVIF. The content decides, whatever the name: a `.heic` that holds AVIF decodes as AVIF.

- **Windows: `grape-heif.exe`**, built from `tools/grape-heif` (its own Cargo workspace and `Cargo.lock`, outside Grape's): libheif-rs 3.0.0 over libheif **1.23.7** (a security release, taken under D9's override), libde265 **1.1.3** and x265 **4.3** for HEIC, and **dav1d 1.5.4** (decode) and **libaom 3.15.2** (encode only) for AVIF, linked statically with the static CRT (`x64-windows-static`). libheif picks the decoder from each image item, so an AV1 grid whose brands sniff as HEIC decodes too. GPL-3.0-or-later as a whole (rule 2): it ships only as this separate executable, with `licenses/grape-heif/` (dav1d's and libaom's BSD-2-Clause texts and the Alliance for Open Media Patent License 1.0 among them) and its source bundle (rule 3).
- **The pin:** `tools/grape-heif/vcpkg.lock.json` holds vcpkg's commit (`e456309`, the last master commit before D9's cutoff), the triplet, the install spec `libheif[core,hevc,aom,dav1d]` and each source archive's URL and hashes (five archives). Two overlay ports in `tools/grape-heif/vcpkg/ports/`: `libheif/` takes that commit's libheif recipe to 1.23.7 (the release tarball, by SHA-512), turns plugin loading off (`-DENABLE_PLUGIN_LOADING=OFF`: with it on, libheif scans its plugin folder even without `LIBHEIF_PLUGIN_PATH`), adds a `dav1d` feature and builds libaom's encoder only (`-DWITH_AOM_DECODER=OFF`); `aom/` takes vcpkg's libaom 3.15.1 recipe to AOM's 3.15.2 release tarball, by SHA-512, its only change. dav1d is vcpkg's own port, unchanged (GitHub's archive of tag 1.5.4, the same release Grape's FFmpeg builds).
- **Build:** `tools/grape-heif/build.ps1`, the same on CI and the PC. It clones vcpkg at the pinned commit (never the runner's), fetches and checks every source archive before it builds, so a binary-cache hit still has the sources for the bundle, then runs `cargo build --release --locked`. vcpkg also fetches Strawberry Perl (libaom), Python and meson (dav1d) and NASM. The first build takes about 45 to 50 minutes and about 5 GB, an estimate until CI measures it (`PLATFORM_WINDOWS.md`).
- **CI:** `.github/workflows/grape-heif.yml`, a reusable workflow that `ci.yml` and `release.yml` call (the release builds it without cache; with cache, vcpkg's binary cache and its `downloads\tools` are kept). It runs the tool's tests, fmt and clippy, checks the banner (`grape-heif version 1.23.7-grape.N`, every pinned library's version, `plugins=disabled`, `crt=static`, `protocol=2`), the probe's exact answer (HEIC and AVIF both ways), that no plugin loader is in the exe, the DLLs it imports (dav1d and libaom must be static) and that the license texts match the built ports and dav1d's archive. It writes the HEIC and AVIF fixtures and decodes and encodes through the worker. It uploads the exe, the fixtures and the source bundle (`grape-heif-<version>-source.tar.gz`: the tool's code and the protocol crate, the vendored crates, the five archives, the vcpkg ports and both overlays, and the build notes). The installer job takes the exe from the same run; the release attaches the source bundle next to the installer.
- **Shipping:** `tauri.sidecars.windows.conf.json` adds `binaries/grape-heif` to `externalBin` (with FFmpeg and bsdtar) and `licenses/grape-heif/` to the resources, and runs the bundling gate (`scripts/check-sidecars.mjs`: the `-grape` marker, `protocol=N` on the banner's configuration line equal to grape-heif-proto's `PROTOCOL` (D41), the license folder and the notices section). Installed, it's `grape-heif.exe` next to `Grape.exe`. It isn't in `scripts/sidecars.lock`, and no GitHub Release carries it on its own until M7.
- **macOS: ImageIO**, through `objc2-image-io`, in `grape_platform::macos::heif`, decodes HEIC and AVIF (AVIF on macOS 13 and later, Grape's minimum). The helper is Grape's own executable, started as `Grape --grape-heif-worker` (like the PDF worker), so nothing more is bundled. A Mac without a HEVC encoder (and GitHub's macOS VMs) can't write HEIC: "This Mac can't write HEIC files." AVIF is written by ravif 0.13.0 and rav1e 0.8.1 (`grape_platform::avif`, BSD-3-Clause and BSD-2-Clause with the AOM Patent License 1.0 in `THIRD_PARTY_NOTICES.md`), compiled into Grape's macOS build only (`avif-encode`); rav1e's arm64 assembly is built for Apple silicon, and the Intel slice is pure Rust. ImageIO's own AVIF encoder (macOS 26 only, and it tiles big pictures into grids) is never used. The worker arms a 2 GiB heap bound (`pdf::heap`, D41) for every job: past it the worker exits 86, "needs too much memory"; ImageIO's own `malloc` isn't counted.
- **How Grape runs it** (`grape-engines` `heif.rs`): `<helper> --grape-heif-worker`, one image per process, its stdin and stdout piped and stderr discarded, `DETACHED_PROCESS` on Windows (no console, so no console host), `LIBHEIF_PLUGIN_PATH` and `LIBHEIF_SECURITY_LIMITS` removed from the environment it inherits, its current folder a new private `grape-heif-…` folder under the OS temp folder, where the raw pixels go both ways. On Windows the app's hook (`grape_engines::set_contain`) puts it in a Job Object before it gets its request: 2 GiB of committed memory, one process, killed when Grape exits, no error dialogs, and UI limits unless Grape itself runs in a job (then the helper's job is nested and can't have them); a helper that can't be contained is killed and the job fails. Timeouts are 120 s plus 1 s per megapixel to decode and 3 s to encode; a cancel kills it within the 100 ms poll. HEIC ⇄ AVIF is two runs, a decode and then an encode, each with its own work folder and deadline. Limits: a HEIF source of at most 512 MiB, at most 134,217,728 decoded pixels, the 1 GiB working set (`image::pixels_fit`, checked from the helper's `image` line before any pixel is read), and at most 35,651,584 pixels to encode, with at most 16,888 a side for HEIC (one HEVC level 6.2 picture) and 16,384 for AVIF (one AV1 level 6 picture), checked before the helper starts (grid encoding is a follow-up).
- **HEIC Compress** (D28, lane B's) runs the same helper through `heif.rs`'s `Encoder` and `Decoder::decode_within`: a probe once per helper (a helper that says it can't write HEIC is refused before anything is decoded; on a Mac that's one whose ImageIO doesn't list `public.heic`, and one that lists it but has no HEVC encoder hears the same words from the encode, after the decode), a decode held to Compress's own peak, and `encode {format: "heic", quality}` with the bytes handed back. Lane B grafts the source's metadata into `out.heic` and checks, on every one, the layout the graft relies on (D33's 2026-10-28 note has the invariants): one that doesn't hold fails the job and publishes nothing. A `grape-heif.exe` bump re-runs the graft's tests; ImageIO's `out.heic` is checked by hand on each new macOS.
- **Bumping:** `tools/grape-heif/README.md` → Bumping. A libheif, libde265, dav1d or libaom security release is likely to come again; take it under D9's override and say so in D33 or D41. ravif and rav1e are crates in Grape's `Cargo.lock`, bumped like any other (D9).

## Subtitles

Grape's own parser and writers (`grape-engines/src/subtitle/`, DECISIONS D20). No crate, no sidecar.

**Reading**
- **Size:** files over 16 MiB are refused unread, and files of over 1,000,000 lines, or with a line of over 64 KiB once read as UTF-8, before anything is written ("… is too large to convert"). A Windows-1252 or UTF-16 line can be shorter than that in the file. A line that a WebVTT `&#10;` or `&#13;` breaks counts once for each line it makes.
- **Encoding:** a BOM first (UTF-8, UTF-16LE, UTF-16BE), then valid UTF-8, else Windows-1252 (WHATWG table). NUL characters are removed.
- **Line breaks:** `\r\n`, `\n` or a lone `\r`. `\r\r\n` is one break, never a blank line: it is what a CRLF file's line ends become when converted again, and it counts as `\r\n` for the output.
- **Format by content:** a file that starts with `WEBVTT` is WebVTT; anything else is read as SRT. Its header lines up to the first blank line are skipped (`Kind:`, `Language:`, `X-TIMESTAMP-MAP=`), and so are `NOTE`, `STYLE` and `REGION` blocks, up to their blank line or to a timing line, which starts a cue.
- **Timing lines** are `start --> end`; cue settings or SRT coordinates after the end are dropped. Timestamps take optional hours, `.` or `,` before the fraction, and 1–3+ fraction digits read as a decimal (`,5` is 500 ms). Minutes or seconds over 59 make the line invalid, and its cue is skipped. In SRT a line with `-->` is a timing line only when it starts with a digit after any spaces, invisible marks (a stray BOM, zero-width and direction marks) and one `-`. So text such as `Go this way -->` or `Route 66 -->` stays text, while a negative timing line from a shifted SRT is still a timing line, and its cue is skipped as invalid. In WebVTT, whose cue text can't hold `-->`, every such line is one.
- **Cues:** a timing line always starts a new cue, even with no blank line before it. A digits-only line just before it is that cue's number. A block with no timing line joins the previous cue's text, unless it is only digits and that cue already has text: then it is a stray number and dropped. Known limit: so a cue with no text, followed by the next cue's number on its own between blank lines (`1`, timing, blank, `2`, blank, timing), shows that number as its text.
- **Styling** is read into italic, bold and underline: `<i> <b> <u>` (with WebVTT classes) and SRT's `{\i1}`/`{\i0}`-style codes. Other `{\…}` codes, `<font>`, `<c>`, `<v>`, `<lang>`, `<ruby>` and inline timestamps are dropped, keeping their text; `<rt>` text goes in parentheses. WebVTT character references are decoded as HTML reads them: the 252 HTML 4 names, case-sensitive (`&eacute;` is é, `&Eacute;` is É), plus `&apos;` and the uppercase `&AMP;`, `&COPY;`, `&GT;`, `&LT;`, `&QUOT;`, `&REG;`, and numbers (`&#233;`, `&#xE9;`). The 106 names of HTML 3.2 (those of U+00A0–U+00FF, such as `&nbsp`, `&copy` and `&eacute`, and `&amp`, `&lt`, `&gt`, `&quot`, `&AMP`, `&LT`, `&GT`, `&QUOT`, `&COPY`, `&REG`) need no `;` when no ASCII letter or digit follows: `&copy 2024` is © 2024, and `&copyé` is ©é. HTML also reads `&copy2024` as ©2024; Grape keeps that as text. Numbers 128–159 are the Windows-1252 characters they stand for there, as in HTML (`&#150;` is –; the five that Windows-1252 leaves undefined stay C1 controls). `&#10;` and `&#13;` break the line; `&#0;`, unknown names, other names without their `;` and numbers without one stay as text. SRT text is taken as is.
- **Normalizing:** cues are sorted by start time, and cues that start together keep their file order; a cue that ends at or before its start gets 1 ms; blank lines and empty cues are dropped. No cue left → "… has no subtitles in it".

**Writing** (UTF-8; line endings follow the source)
- **WebVTT:** `WEBVTT`, then cues numbered 1…n, `HH:MM:SS.mmm --> HH:MM:SS.mmm`, and text with `&`, `<` and `>` escaped. No BOM.
- **SRT:** cues numbered 1…n, `HH:MM:SS,mmm --> HH:MM:SS,mmm`, and raw text; a `-->` inside text is written `->`. A UTF-8 BOM unless the source was BOM-less UTF-8.
- **Styling:** `<i> <b> <u>`, balanced within each cue.
- **TXT:** only the text, one line per subtitle line, with no timings or blank lines; a line identical to the one before is written once. No BOM.

**Known limits**
- **Cancelling:** after a cancel, the job can take longer to return than the 50 ms allowed between checks. Freeing a large parsed file, an fsync already under way and removing a large temp file add up to about 150–200 ms on the largest files, depending on the disk. Measured in release builds: up to 147–196 ms for 16 MiB files dense with tags or a conversion with an 80 MiB output, and 57–99 ms for a realistic 16 MiB SRT (once 244 ms).
- **SRT text that looks like a timing line:** a text line with `-->` that starts with a digit, or with `-` and a digit (`10 degrees --> brr`, `-10 degrees --> brr`), is read as a timing line. Its timing is invalid, so it and the rest of its cue are dropped, and so is a line of only digits right before it, taken for its cue number. A cue whose text starts there is dropped whole. It follows from the rules under Timing lines.

## Metadata removal
Audio, video and the four image formats are in (D26).

- **PDF:** clear the `Info` dictionary and XMP `Metadata` stream with lopdf, and write the whole file again so old revisions go too (D29). Page-level XMP and image metadata stay.
- **Images** (JPG, PNG, WebP, GIF; D26): a container-level strip in Rust, with no decode, so the image data stays byte for byte. The container is picked by its magic bytes, not the name (a PNG named `.jpg` is stripped as a PNG and keeps its name). Kept parts are copied as they are; counts are capped, loops refused, and a damaged file writes nothing.
  - JPEG keeps SOI, a JFIF APP0 (its thumbnail removed), the ICC profile (APP2), Adobe's APP14, the tables, frames and scans, and EOI. It drops EXIF and XMP (APP1), JFXX thumbnails, MPF and FlashPix (APP2), IPTC (APP13), APP3–APP12 and APP15 (C2PA included), comments, and everything after the first image's EOI: gain maps, depth maps, Samsung's trailer and motion-photo video (padding of zero or FF bytes there isn't reported; what follows is read up to its first other byte, however far). Stray bytes between segments, before the first scan or between scans, which libjpeg skips too, are dropped unreported. A scan's entropy-coded data is copied byte for byte, its fill bytes included, except those before the marker that ends it. The header segments (at most 1024) are held until the first scan, then the scans are copied as they're read.
  - PNG keeps the image, color and layout chunks (ICC, sRGB, gamma, cICP, mDCV, cLLI, pHYs, …) and APNG's frames, and drops text chunks (their keyword says what they held, and compressed text is inflated only until it isn't blank, 64 KiB of it at most and 16 MiB in a file, and text blank as far as it was read is reported all the same; ImageMagick's raw EXIF profile is read as EXIF, from its own 1 MiB allowance and then the text's, whatever the text before it cost, and as far as it goes when cut short (the rest reported as other fields; one without an EXIF header is other fields alone)), `eXIf` (one over 1 MiB is read as far as its first 1 MiB, which holds its first IFD, and the rest reported as other fields), `tIME`, unknown ancillary chunks and anything after IEND. Apple's `iDOT` goes too, unreported: its offsets would be wrong. The minimal EXIF goes back as `eXIf` only when the old one came before the image data (and an sRGB chunk, like an ICC profile, rules out the Adobe RGB one).
  - WebP keeps `VP8 `, `VP8L`, `VP8X` (its 10 bytes are all that's held), `ALPH`, `ANIM` and `ICCP`, and each `ANMF` frame with its header and its `ALPH`, `VP8 ` or `VP8L`; it drops `EXIF` (one over 1 MiB as for PNG), `XMP `, unknown chunks, inside a frame too, and anything after the RIFF, and fixes the RIFF size, each frame's size and the VP8X flags. A frame holding `ANMF`, `VP8X`, `ANIM` or `ICCP` is refused as damaged: libwebp reads such a frame's tail as more frames and the `image` crate doesn't, so no output is sure to keep them all. A simple WebP (no VP8X) has no EXIF flag to set, so no minimal EXIF goes back into one.
  - GIF keeps the images, their palettes, the graphic control and plain text extensions, the first loop extension and an ICC profile, and drops comments, XMP, IPTC, other application and unknown extensions, later loop extensions (unreported), an empty application extension (`21 FF 00`, reported as other fields) and anything after the trailer.
  - EXIF is read (both byte orders, IFD0, Exif, GPS, Interop and IFD1; MakerNote isn't followed; at most 8 IFDs of 1024 entries) only to say what it held. Tags that only describe the picture (size, resolution, bit depth, color layout, orientation, the Exif and Flashpix versions) and empty values aren't reported; a GPS IFD with only its version isn't a location. When the photo has an Orientation other than 1, or says it's Adobe RGB the DCF way (no ICC, ColorSpace 0xFFFF, Interop `R03`), a new EXIF holding only that takes the old one's place, so nothing turns or shifts color.
- **Audio and video** (MP3, M4A, WAV, FLAC, MP4, MOV, MKV; D26): `-c copy -map_metadata -1 -map_chapters -1 -fflags +bitexact`, never a re-encode. Kept: every video that isn't cover art, nor a cover a copy turned into a video track (FFmpeg copies an MKV's image attachment back as a one-frame video track without the cover-art mark, and copies that on into an MP4 or MOV as it is: a still-image track (PNG, JPEG, BMP, WebP, GIF, TIFF) beside another video is dropped and reported as cover art when it holds one frame by what the container says, the frame count in an MP4 or MOV (a fragmented one counts none, so such a cover stays in it), or in an MKV, which counts none, the attachment's `mimetype` tag (`image/…`) it kept. In an MP4 or MOV a track of more than one frame is always video; a camera's MJPEG track has no MIME type and stays, and so does a copied cover that is the only video; an M4A, which keeps no video, reports such a track as the cover art it drops), every audio track, MP4/MOV `mov_text` and MKV subtitles, MKV fonts, each track's language (set again), dispositions, rotation, HDR and Dolby Vision boxes (`-strict unofficial`). Dropped: every tag, chapters (with MP4's and M4A's chapter track, a QuickTime text or timed-text track, reported as chapters), cover art, data tracks (GoPro GPMF, camm, timecode, `mebx`), MKV image and other attachments, and MP4/MOV timecode (`-write_tmcd 0`). MP3 gets no ID3 tag at all (`-id3v2_version 0`); WAV no INFO list. The output is probed for tags again, and anything besides structural keys (brands, a bare `Lavf` encoder, FFmpeg's handler names, `vendor_id`, languages, MKV `DURATION`, fonts' names and types) fails the job before anything is published.
- **The report** (`JobOutcome::notes` → `Note::MetadataRemoved`; the app words it): what was removed, by kind: location, camera, author, title, subject, keywords, comments, copyright, creator, producer, software, dates, XMP, IPTC, thumbnail, cover art, chapters, embedded media and other fields. Media is reported from the source's tag keys (the tags probe, Tools above), and a copied MKV cover as cover art when it's dropped; images from the parts actually dropped. An image or media file with none says "No metadata found"; a PDF "No document metadata found".
- **Limits:** TIFF and HEIC are coming (D28); user data inside an H.264 or HEVC bitstream (SEI) can't be removed by a copy; XMP is reported as XMP even when it holds a location; unknown MP4 `udta`/`uuid` boxes (Sony, DJI, GoPro), ID3 GEOB frames and WAV `iXML`, `axml` and `_PMX` chunks are removed but not reported, since ffprobe doesn't show them. ID3 PRIV frames are shown (`id3v2_priv.<owner>`, reported as other fields), and a WAV's `cue ` points are its chapters (`wavdec.c`), reported as chapters.
