# macOS platform notes

Target: macOS 13+ on **Apple silicon and Intel**. Ship a universal binary, since Tangerine is Apple-silicon-only and Intel support is cheap for us. Rust bindings: `objc2`, `objc2-app-kit`, `objc2-foundation`.

## Detecting a file drag without special permissions

Goal: no Accessibility or Input Monitoring prompt. **[Grape design]** It's *inferred*, not observed, that Tangerine works similarly, since it ships sandboxed on the Mac App Store.

Built as `grape_platform::macos::MacDragMonitor` (D18):

1. **Drag pasteboard.** `NSPasteboard(name: .drag)` (`NSPasteboardNameDrag`) changes its `changeCount` when a new drag session begins anywhere in the system.
2. **Poll only while the mouse is down.** A `grape-drag` thread checks `NSEvent.pressedMouseButtons() & 1` every 100 ms while the button is up, and every 8 ms (~120 Hz) while the left button is held. (A global `NSEvent` mouse monitor was the alternative; polling needs no run loop and was simpler.)
3. **Started:** as soon as a poll sees that the drag pasteboard's `changeCount` changed since the button was last up and its `types` include `public.file-url`, the tracker sends `DragSignal::Started`. AppKit only starts a drag session once the pointer has moved past its own threshold, so Grape adds no 4-point check of its own. The keys held when Grape first sees that drag session are the baseline and don't open a wheel (D14), as on Windows where they're read at the threshold. A key pressed after that opens the wheel, even while the pointer rests. A key tapped and released before Grape sees the session (up to a tenth of a second) is missed. Known gap: if a whole file drag ends and a new press starts within one idle poll, the new press looks like a file drag too; a key tapped during a plain click-and-hold then shows an empty ring, which closes on the next move or on release. Grape checks only the *types*. It never reads the pasteboard's contents, because recent macOS can ask the user before an app reads a pasteboard. The paths arrive with the overlay's drop `Enter`, as on Windows.
4. **Modifiers:** poll `NSEvent.modifierFlags()` (class property, no permission needed) on the same thread. Map `.shift`, `.control`, `.option` and `.command` to shift, ctrl, alt and meta.
5. **Cursor:** `NSEvent.mouseLocation()` is in *bottom-left-origin* points. Grape's global coordinates on macOS are **points with the origin at the top-left of the primary (menu-bar) screen**, y down, the same space as `CGDisplayBounds`. With H the primary screen's height: cursor = (x, H − y), and a screen frame F becomes {F.x, H − (F.y + F.h), F.w, F.h}. `DisplayBounds.scale` is 1.0, so 1 unit = 1 point = 1 CSS pixel in the overlay. Screens left of or above the primary one have negative coordinates.
6. **Drag ends** when the button goes up → `DragSignal::Ended`.
7. **Esc** can't be read without Input Monitoring (D7), so `Escape` is never sent. Esc cancels the AppKit drag session, which the overlay sees as a drop `Leave` while the button is still down; the controller treats that as Esc (below). That only works while a wheel is open and the cursor is over it on the wheel's display. Esc before any wheel opens can't be seen at all: a key tap while still holding the button then shows an empty ring, which closes on the next move or on release. Esc on another display leaves the ring up until the button goes up. The drag itself is cancelled either way, so nothing is dropped.
8. **App Nap:** with every window hidden, macOS may nap a menu-bar app and stretch its timers. The drag thread holds an `NSProcessInfo` activity (user-initiated, idle system sleep allowed) for as long as it runs, so its polls stay on time.

If the drag pasteboard has no file URL type (text, browser images, promised files), the wheel never opens.

**File promises** (e.g. dragging from Photos or Mail) arrive as `NSFilePromiseReceiver`. Treat them as v2 and close the wheel for now.

## Overlay window
- Tauri window as described in `ARCHITECTURE.md`. `macos::harden_window` (main thread) sets level `.popUpMenu` (101) and adds `.canJoinAllSpaces`, `.fullScreenAuxiliary`, `.stationary` and `.ignoresCycle` to `collectionBehavior`, with `hidesOnDeactivate` off. Never use a level of 500 or more: the system's drag image sits there, and covering it hides what the user is dragging. The toast gets the same behavior one level lower (100, `WindowRole::Toast`), so the full-display overlay always covers it and a progress update can't put it above an open wheel.
- **Showing:** `macos::frame_and_show` sets the frame (Grape's top-left points turned into a Cocoa rect) and calls `orderFrontRegardless` in one main-thread call; that orders the window front although Grape isn't the active app. `"focusable": false` is what keeps the overlay and toast from ever becoming key. Never call `activate`, `set_focus`, `set_always_on_top` or `set_fullscreen` on them: the first activates Grape, and tao's level setters reset the level. Hiding uses Tauri's `hide()`.
- `"backgroundThrottling": "disabled"` keeps a hidden overlay's page running (macOS 14+), so the wheel is drawn by the time the window appears. The toast has `"acceptFirstMouse": true`, so one click on it reveals the output while another app is active.
- **Tool panel** (D31): the `panel` window is the one hardened window that becomes key (`"focusable": true`; tao's borderless window answers `canBecomeKeyWindow` from it). `harden_window(…, WindowRole::Panel)` gives it level 99, under the toast (100) and the overlay (101), so an open wheel and a toast always cover it, with the overlay's collection behavior. `macos::show_panel` records the app in front, sets the frame, `orderFrontRegardless`, `makeKeyWindow`, then Grape's own `activate()` (`NSApp.activate` on 14+), never tao's `set_focus`. macOS may decline the activation right after a drop; the panel is then visible but inactive, and the first click activates Grape and, through `"acceptFirstMouse": true`, reaches the control. Esc and Enter reach the page only while the panel is key (D7: no key monitors); × and Cancel always work. An Esc the page gets while a mouse button is down (`macos::mouse_button_down`, `NSEvent.pressedMouseButtons`) is refused by `panel_cancel` and the page takes input again: a file dragged out of a Finder window behind the key panel can leave Grape active, so that drag's Esc would reach the panel instead of ending the drag. Whether Finder lets that drag start without activating, and where its Esc goes, is a Mac check. `macos::hide_panel` orders it out and, if it was key and Grape is still active, `hand_back`s activation to the app that was in front (looked up by pid). Never `NSApp.hide`. A file dropped on the panel is accepted as a copy by wry and ignored (D18).
- If drops over full-screen apps fail, switch to a non-activating `NSPanel` (`tauri-nspanel`). Logged as a known risk; check it with the `mac:` QA lines.
- The overlay must not activate Grape, so the frontmost app keeps focus. The whole app uses `ActivationPolicy::Accessory` (menu-bar only, no Dock icon), set before the event loop starts, with `LSUIElement` in `Info.plist`. Opening Grape.app again opens Settings.

## Drops on the overlay
- wry's own drop handler is the drop target, reported as Tauri's `WindowEvent::DragDrop` (`dragDropEnabled: true`). It accepts the drag as a **copy**, so Finder never moves the file. Its positions are points relative to the window's top-left (typed as `PhysicalPosition`), and the app adds the overlay's frame origin to make global `DropEvent`s.
- **Command or Control held:** Finder limits the drag to "generic" or "link" while those keys are down, and AppKit may then refuse wry's copy, so no `Drop` arrives. With Command or Control held at release over the overlay and no `Drop` within the drop grace (750 ms), the controller runs the highlighted segment itself (`ControllerConfig::release_fallback`). A refused drop's `Leave` can come just before or just after the button-up, so a release within 50 ms after a `Leave` counts too; a later release (Esc, then letting go) runs nothing. It never runs twice. Shift drops are normal drops.
- **Esc:** a `Leave` while the button is still down, with the cursor still on the wheel's display, starts a 200 ms grace (`ControllerConfig::leave_ends_drag`). An `Enter` or `Over` within it was a flicker, and the wheel carries on. A button-up within 50 ms of the `Leave` is a release (above). A move onto another display keeps the wheel with nothing highlighted. Otherwise the wheel closes as for Esc and stays out of the way until the button goes up.
- **The toast** has `dragDropEnabled` too, so wry accepts a file dropped on it as a copy and nothing happens; the file is never moved. While a wheel is open, the overlay covers it.

## Haptics and sound
- Tick: `NSHapticFeedbackManager.defaultPerformer.perform(.alignment, performanceTime: .now)`, as `grape_platform::haptic_tick()`, on each new highlighted segment while the "haptics" setting is on (D19).
- Sound: play our own short tick via `NSSound` (preloaded) or WebAudio in the overlay. It must start within 10 ms.

## File actions
- Share: `NSSharingService(named: .sendViaAirDrop)?.perform(withItems: urls)` on the main thread, after activating Grape so the AirDrop window comes to the front. A delegate hands activation back to the app that was in front once AirDrop reports it's done, failed or was cancelled, unless an AirDrop window is still open; then Grape stays active until the user clicks elsewhere.
- Copy: write `NSURL`s to `NSPasteboard.general` after `clearContents()`. Copy Path: the paths as one string, one per line.
- Move: `NSOpenPanel` ("Move Here", directories only) on the main thread, then `FileManager.moveItem` on the action's own thread. It never overwrites: an item whose name is taken in the chosen folder stays where it was. A mounted volume's root (a USB stick, a DMG or a network share dragged from the Desktop or the sidebar) is never moved, because moving it would copy its contents and then erase them. There's no system undo for this, so moving to another volume asks "Move to another drive?" first, with Cancel as the default button. Grape activates itself for the panel and the alert, then hands activation back to the app that was in front. Each item's result is recorded right after its own move, and the toast says what moved and reveals it.
- Terminal: `open -a Terminal <dir>`, or `open -b com.googlecode.iterm2 <dir>` when the user chose iTerm2 in Settings and Launch Services finds it (otherwise Terminal, with a log line).
- Reveal (toast click): `open -R <path>`.
- Float: not on the Mac yet. Control-drop on FLOAT shows "Not in this build yet", because a drag out of the shelf needs an `NSDraggingSession` (D21).

## Conversions that use Apple frameworks
- **HEIC encode/decode (D33):** ImageIO, in the HEIC worker: Grape's own executable started again as `Grape --grape-heif-worker` (`main.rs`, `grape_platform::macos::heif::ImageIo`), once per HEIC job, with no window or menu-bar item, speaking the HEIC protocol (`crates/grape-heif-proto`) that `grape-heif.exe` speaks on Windows. Grape's own process never decodes a HEIC. It's the native, licence-free path, so there's no libheif on macOS.
  - *Decode:* the primary image's size and bit depth come from its properties first: over 134,217,728 pixels, or a decode that wouldn't fit the request's 1 GiB decoder budget (about 8 bytes a pixel at 8 bits and 12 above, Grape's bitmap included, `mac_rules::heif_decode_bytes`; libheif holds to the same budget on Windows), is "too large", before anything is decoded. Then `CGImageSourceCreateThumbnailAtIndex` with `FromImageAlways`, `WithTransform` (irot and imir applied, so it's upright) and the full size as the maximum gives the picture. The picture is drawn into an 8-bit RGBA bitmap in the image's own RGB color space with that space's ICC profile (Display P3 for PQ or HLG; sRGB with no profile for anything else) and let go. Only then does the `image` line go out, before any pixel is written, so the parent's `pixels_fit` can still stop the job: with 3 channels when the source says it has no alpha or every pixel drawn is opaque (ImageIO's full-size thumbnail has alpha even for an opaque HEIC), else 4, with the alpha un-premultiplied. A picture that isn't exactly full size is refused.
  - *Encode:* first `CGImageDestinationCopyTypeIdentifiers` must list `public.heic`. Macs without a hardware HEVC encoder, and GitHub's macOS VMs, don't, and the toast says "This Mac can't write HEIC files." Some list it and still can't: ImageIO makes the destination and then `CGImageDestinationFinalize` fails, which says the same. Otherwise one picture at ImageIO's lossy quality 0.8, upright, with the source's RGB profile.
  - *Hardening:* on macOS 14.2 and later the worker restricts ImageIO to `public.heic`, `public.heif` and `public.heics` first thing, before ImageIO does anything else and while the worker has one thread (`CGImageSourceSetAllowableTypes`, looked up with `dlsym`: a bound import would stop Grape launching on macOS 13, so CI's DMG job checks `nm -um` doesn't list it). The worker ends itself when Grape goes away, and the engine kills it on cancel or timeout.
  - *Tested:* CI's `heif-it-macos` decodes the HEICs the Windows job makes with libheif (`crates/grape-platform/tests/heif_imageio.rs`), and the DMG job probes the worker. Encoding has never run on a real Mac: that's manual QA (`TESTING.md` → HEIC).
- **H.264/HEVC encode:** FFmpeg `h264_videotoolbox` / `hevc_videotoolbox`. Hardware, fast, and avoids x264 on Mac.
- **v2 documents:** `NSAttributedString` reads and writes `docx`, `rtf`, `rtfd`, `html` and `odt` natively. **[inferred]** This is a plausible route for Tangerine's DOCX/RTF/RTFD support. Text clippings are `.textClipping` resource-fork-style plists; read the `utf8` / `public.utf8-plain-text` data.
- **Pages:** no public API. `NSAttributedString` can't read `.pages`. See `DECISIONS.md` O2.

## Sidecars

**The lock's builds are for dev testing only.** The prebuilt FFmpeg builds the lock pins today are never bundled: the DMG carries Grape's own minimal FFmpeg, which CI builds (DECISIONS D24, lane B's `scripts/ffmpeg/build.sh`), and the lock will point at Grape's own release at M7 (D25).

FFmpeg and ffprobe are separate programs that Grape runs (golden rule 6). They aren't in the repo. A script fetches the builds pinned in `scripts/sidecars.lock` (D25; the pin itself is D22). Run it from the repo root:

```bash
./scripts/fetch-sidecars.sh           # fetch, unless they're already current
./scripts/fetch-sidecars.sh --force   # fetch again anyway
```

- It needs `curl`, `shasum`, `unzip`, `/usr/bin/tar`, `lipo`, `codesign`, `arch` and `python3`, which reads the lock. `lipo` and `python3` come with the Xcode Command Line Tools (`xcode-select --install`), which Rust needs anyway. It runs in macOS's own bash 3.2.
- **What lands where.** `apps/desktop/src-tauri/binaries/`, which git ignores, gets:
  - `ffmpeg-aarch64-apple-darwin` and `ffmpeg-x86_64-apple-darwin`, and the same two for `ffprobe`: Martin Riedl's release builds, one zip each (28 to 34 MB). tauri-build looks for these while a universal build compiles each arch.
  - `ffmpeg-universal-apple-darwin` and `ffprobe-universal-apple-darwin`: each pair merged with `lipo -create`, then signed ad hoc (`codesign --force --sign -`), because lipo breaks Riedl's own signature. These are the ones the bundler puts in Grape.app.
  - `sidecars.stamp`, written last: the lock's SHA-256, the target, and each file's SHA-256.
  - No license text: the Riedl zips carry none. They're for dev testing only and never ship; the DMG carries Grape's own build, with its texts from `licenses/ffmpeg/`.
- **The checks.** Each zip downloads into a new temp folder with `curl --fail --location --proto =https`, and redirects must stay on HTTPS too. Its size and SHA-256 must match the lock before anything is extracted. On a mismatch it's deleted and nothing changes. Only the file the lock names is extracted. `lipo -archs` must show arm64 and x86_64 in the right files and both in the universal one, and `codesign --verify --strict` must pass. The universal file then runs with `-hide_banner -version`: the first line must name the lock's version, and the configuration line must not have `--enable-nonfree`. On Apple silicon with Rosetta the Intel half runs too; otherwise the script says only this Mac's half ran. Only after every check passes do the files replace the ones in `binaries/`. The temp folder is always deleted.
- **A second run** reads the stamp. If the lock, the target and every file still match, it says the sidecars are already current and stops. If anything differs, it fetches again.
- It doesn't change `PATH` or install anything. This script is the only download, at build time. Grape itself never downloads anything (golden rule 3).
- **CI** runs it in the Sidecars job on `macos-latest` with `/bin/bash`, then again (it must find them current), and lists the files and `lipo -info`. `binaries/` is cached by the hashes of the lock and both fetch scripts, so a changed script runs in full. The job builds nothing.
- **In the DMG.** `apps/desktop/src-tauri/tauri.sidecars.macos.conf.json` adds both, and Grape's bsdtar ("bsdtar (RAR)", below), to `bundle.externalBin` for a build that passes it (from `apps/desktop`), with `licenses/ffmpeg/` and `licenses/libarchive/`. It's the one macOS overlay that sets `externalBin` (a second one would replace its list); the PDFium overlay sets only frameworks and resources, so they go together. Before the build it runs the gate, `scripts/check-sidecars.mjs` (D25), on the merged list in `TAURI_CONFIG`. The gate refuses anything but Grape's own FFmpeg build (its version line ends in `-grape`, D24) with `licenses/ffmpeg/` (the license texts, and `SOURCE.md` with the source link) and its `THIRD_PARTY_NOTICES.md` section, and anything but Grape's own bsdtar (its `-grape` marker) with `licenses/libarchive/` and its section (D27). So the lock's Riedl build works for `tauri dev` only. The DMG carries FFmpeg now that CI builds it (D24): CI's `ffmpeg` workflow runs `scripts/ffmpeg/build.sh` for `macos-arm64` on an Apple silicon runner (`macos-latest`) and for `macos-x86_64` natively on an Intel one (`macos-15-intel`: `uname -m` must say x86_64, so Rosetta isn't enough), then joins each pair with `lipo` into `<name>-universal-apple-darwin` and signs it ad hoc, keeping the per-arch files next to it (tauri-build looks for them while a universal build compiles each arch, D25). CI's DMG job takes them from the same run, puts bsdtar there too, and builds with `--config src-tauri/tauri.pdfium.macos.conf.json --config src-tauri/tauri.sidecars.macos.conf.json`.
- **Or take CI's build** to test the FFmpeg the DMG ships: download the `ffmpeg-apple-darwin` artifact from a CI run (the `ffmpeg` workflow) into `apps/desktop/src-tauri/binaries/`. It holds the `-aarch64-apple-darwin`, `-x86_64-apple-darwin` and `-universal-apple-darwin` files for both programs, with `BUILDINFO-macos-*.txt`, `SHA256SUMS` and `licenses/ffmpeg/`. Artifacts lose the executable bit, so `chmod +x` them, and clear the quarantine flag a browser download sets (`xattr -d com.apple.quarantine apps/desktop/src-tauri/binaries/ff*`; `gh run download` sets none). The same run's `ffmpeg-source` artifact is its complete source.
- **In dev**, `pnpm tauri dev --config src-tauri/tauri.sidecars.macos.conf.json` makes tauri-build copy this Mac's per-arch files into `target/debug` as `ffmpeg` and `ffprobe`, next to Grape's executable, with `bsdtar`. tauri-build fails the build if any file the overlay lists is missing from `binaries/`, and this script brings only FFmpeg, so put a bsdtar there first, even to test only FFmpeg: `./scripts/bsdtar/build.sh --install` or CI's artifact ("bsdtar (RAR)", below).
- **Installed**, they lose the suffix: `Grape.app/Contents/MacOS/ffmpeg` and `ffprobe`, next to Grape's executable, with their texts in `Contents/Resources/licenses/ffmpeg/`. That's where `src/sidecars.rs` looks, never on `PATH`. Without either one an audio or video drop says "Grape's media converter is missing" / "Reinstalling Grape brings it back." (D35). The bundler signs them again with the app's identity (ad hoc for now). Notarization (M9) needs each signed with the Developer ID and the hardened runtime (Distribution, below).
- **Intel:** Riedl's Intel release builds stop in January 2027. A pin after that needs another Intel source (D22).
- `GRAPE_SIDECARS_NO_RUN=1` skips lipo, codesign and the `-version` run, places only the per-arch files (and PDFium unsigned), and writes no stamp, so the download can be tested on another OS. It's for testing only. The next run without it checks everything again.

## PDFium

PDFium is the library Grape reads PDFs with (DECISIONS D29). Every installer and DMG carries it, as they carry FFmpeg. It isn't in the repo either: the same script fetches it, as pinned in `scripts/sidecars.lock` → `libraries`. A plain run fetches it with the sidecars; `--only pdfium` fetches just it (7.1 MB):

```bash
./scripts/fetch-sidecars.sh --only pdfium
```

- **What lands where.** From bblanchon's universal `pdfium-mac-univ.tgz` for `chromium/8086`, extracted with `/usr/bin/tar`:
  - `binaries/libpdfium-universal-apple-darwin.dylib` (15 MB, arm64 + x86_64; it's universal already, so no lipo merge);
  - the same file as `binaries/macos/libpdfium.dylib`, because `bundle.macOS.frameworks` keeps a file's name and Grape looks for `libpdfium.dylib`.
  - Both get their lines in `sidecars.stamp`, and with `--only` the other files keep theirs.
- **The checks.** The archive's size and SHA-256 must match the lock, then the dylib's own SHA-256. It can't be run, so there's no `-version` check. `lipo -archs` must show arm64 and x86_64. The build signs only the arm64 half (linker-signed), so the script signs the whole file ad hoc (`codesign --force --sign -`) and checks it with `codesign --verify --strict`. The signed file no longer has the lock's hash, so a second run compares it with the stamp, as for the sidecars.
- **In Grape.app.** A build that passes `--config src-tauri/tauri.pdfium.macos.conf.json` (from `apps/desktop`) puts it in `Grape.app/Contents/Frameworks/libpdfium.dylib`, and its license texts in `Contents/Resources/licenses/pdfium/`. The bundler signs the dylib (ad hoc for now) before it signs the app. It goes in `Frameworks`, not `Resources`, because files in `Resources` are sealed as data, not signed as code. CI's DMG job does this and checks it, with the macOS sidecars overlay after it ("Sidecars", above): `pnpm tauri build --target universal-apple-darwin --bundles app,dmg --ci --config src-tauri/tauri.pdfium.macos.conf.json --config src-tauri/tauri.sidecars.macos.conf.json`. A build or `tauri dev` run without it has no PDFium, so a PDF drop says "Grape's PDF library is missing" / "Reinstalling Grape brings it back." (D35; in dev, that means passing this overlay). In dev that holds only until a run with the overlay: tauri-build leaves `target/Frameworks/libpdfium.dylib` behind (it clears that folder only when a run has frameworks), and later plain runs find it. Delete it to see the toast. The overlay fails the build while the dylib isn't fetched.
- **In dev**, `pnpm tauri dev --config src-tauri/tauri.pdfium.macos.conf.json` makes tauri-build copy it to `target/Frameworks/libpdfium.dylib` (`target/<triple>/Frameworks/` for a `--target` build) and add an `@executable_path/../Frameworks` rpath. So `../Frameworks/libpdfium.dylib` from Grape's executable is right in dev and in Grape.app alike.
- **Who loads it.** Only the PDF worker: Grape's own executable started again as `Grape --grape-pdf-worker`, once per PDF job, with no window or menu-bar item. It loads the dylib by its full path, never from the system. Grape's main process never loads it, so a crash on a bad PDF ends only that job.
- **Hardened runtime off for now.** `tauri.conf.json` sets `bundle.macOS.hardenedRuntime: false` while the DMG is signed ad hoc. The hardened runtime turns on library validation, which loads only code signed by Apple or with the app's own Team ID. Ad-hoc code has no Team ID, so the ad-hoc DMG would most likely refuse the ad-hoc dylib. That's unverified, the first thing to check on a Mac. An ad-hoc app can't be notarized anyway, so nothing is lost now. With Developer ID (M9) the bundler signs the dylib with the app's identity, the Team IDs match, and the hardened runtime goes back on, with no `disable-library-validation` entitlement. CI's DMG job fails if Grape.app has the runtime flag.
- **Tests.** `cargo test -p grape-engines --features pdf-it` runs the tests that need PDFium. They fail, not skip, without `GRAPE_TEST_PDFIUM`, the dylib's full path: `GRAPE_TEST_PDFIUM="$PWD/apps/desktop/src-tauri/binaries/libpdfium-universal-apple-darwin.dylib"` from the repo root. CI's Rust job runs them after fetching PDFium only. Test binaries aren't signed with the hardened runtime, so they never meet library validation.

## bsdtar (RAR)

Grape reads RAR archives with `bsdtar`, a separate program it builds from libarchive 3.8.10 and its own patches (DECISIONS D27). It isn't in the repo or in `scripts/sidecars.lock`. To build it on a Mac, from the repo root:

```bash
./scripts/bsdtar/build.sh --install
```

- **What it needs:** the Xcode Command Line Tools (`clang`, `lipo`, `codesign`, `vtool`, `otool`, `python3`, `git`) and CMake 3.23 or later. It runs in macOS's own bash 3.2 and downloads only libarchive's release tarball, checking its size and SHA-256 before anything is extracted.
- **What lands where.** `target/bsdtar/out/` gets `bsdtar-aarch64-apple-darwin`, `bsdtar-x86_64-apple-darwin` and `bsdtar-universal-apple-darwin` (the two merged with `lipo`), all three signed ad hoc, minimum macOS 13.0, with `BUILDINFO.txt` and `SHA256SUMS`; `--install` copies them into `apps/desktop/src-tauri/binaries/`. Before it reports success it checks that each links only `/usr/lib/libSystem.B.dylib`, holds the right architectures, says `minos 13.0` and passes `codesign --verify --strict`, and that the version line is exactly `bsdtar 3.8.10-grape.1 - libarchive 3.8.10 CommonCrypto/system libb2/bundled ` (also for the Intel half, under Rosetta). `--check-only` runs the checks again. Or download CI's `bsdtar-apple-darwin` artifact into that folder and `chmod +x` the files. A browser download marks them as quarantined, and macOS then refuses to run them (they're signed ad hoc, not notarized), so clear the flag: `xattr -d com.apple.quarantine apps/desktop/src-tauri/binaries/bsdtar-*`. `gh run download` sets no flag.
- **Installed**, it's `Grape.app/Contents/MacOS/bsdtar`, next to Grape's executable, with `Contents/Resources/licenses/libarchive/`: it ships in `tauri.sidecars.macos.conf.json` with FFmpeg, and CI's DMG job takes it from the same run's `bsdtar` workflow. Grape looks for it only there, never on `PATH`. Without it a RAR drop says "Grape's RAR helper is missing" / "Reinstalling Grape brings it back.", and the log's `sidecars:` line says bsdtar is missing (D35).
- **`LC_ALL=en_US.UTF-8` is required.** Grape runs bsdtar with `TAR_READER_OPTIONS=rar:hdrcharset=UTF-8`, and without a UTF-8 locale that makes it fail on every RAR. CI's smoke test runs with exactly Grape's environment, so a Mac without that locale would show there.
- **Names come back NFD.** Apple's libarchive decomposes the names it reads; Grape makes them NFC again before it checks and writes them.
- **Tests.** `GRAPE_TEST_BSDTAR="$PWD/target/bsdtar/out/bsdtar-universal-apple-darwin" cargo test -p grape-engines --features rar-it --lib archive::rar`. CI runs them against the bsdtar it built in the same run.
- Nothing here has run on a Mac by hand yet: CI builds and tests it until Maxwell runs a DMG.

## Running a CI build

Every CI run builds `Grape-macOS-universal`, a DMG with a universal (Apple silicon + Intel) Grape.app. It's ad-hoc signed but not notarized (D18; notarization comes with M9), so macOS will refuse to open it at first.

1. Open the run on GitHub (Actions → CI → the run for the commit). Under **Artifacts**, download `Grape-macOS-universal` and unzip it.
2. Open the `.dmg` and drag **Grape** into **Applications**.
3. Launch Grape once. macOS says it can't check it for malware. Click **Done**.
4. Open **System Settings → Privacy & Security**, scroll to Security, and click **Open Anyway** next to "Grape was blocked". Confirm with your password.
   - Or, in Terminal: `xattr -dr com.apple.quarantine /Applications/Grape.app`, then open Grape normally.
5. Grape appears in the menu bar (no Dock icon). Quit it from its menu.

## Distribution
- **Direct download first:** a DMG signed with **Developer ID**, hardened runtime, **notarized** and stapled. Every sidecar binary must be signed with the same identity and hardened runtime, or notarization fails. `libpdfium.dylib` needs the same identity too, for library validation. Today's ad-hoc DMG has the hardened runtime off (PDFium, above; D29).
- Entitlements: none needed for drag/modifier polling. Add `com.apple.security.cs.disable-library-validation` **only** if a sidecar loads unsigned dylibs (avoid this).
- Mac App Store is **later**. The sandbox complicates writing outputs next to sources: a dropped file grants access to that file, not its folder. It would need security-scoped bookmarks or a user-chosen output folder. Tracked in `DECISIONS.md`.
- Auto-update: `tauri-plugin-updater` with signed update manifests on GitHub Releases. It's the *only* allowed network call (rule 3), and it's opt-in.

## Mac QA must-checks
- Drag from Finder, the Desktop, Downloads stack, Spotlight results, and the Finder sidebar.
- Full-screen app in front. Two displays with different scale factors. Stage Manager on.
- Drop outside the ring cancels and Finder does **not** move the file.
