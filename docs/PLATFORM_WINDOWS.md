# Windows platform notes

Target: Windows 10 22H2+ and Windows 11, x64 and ARM64. WebView2 is preinstalled on 11. On 10, Tauri's bootstrapper installs it. Rust bindings: the `windows` crate.

## Dev setup (on the Windows PC)

Install these once, in PowerShell:

```powershell
winget install --id Git.Git -e
winget install --id Microsoft.VisualStudio.2022.BuildTools -e --override "--wait --passive --add Microsoft.VisualStudio.Workload.VCTools --includeRecommended"
winget install --id Rustlang.Rustup -e
winget install --id OpenJS.NodeJS.LTS -e
```

Then open a **new** terminal and run:

```powershell
rustup default stable-msvc
rustup target add aarch64-pc-windows-msvc   # only if building ARM64 too
npm install -g pnpm@10
```

- WebView2 is built into Windows 11. On Windows 10, install the Evergreen runtime if `pnpm tauri dev` asks for it.
- Check the setup with `rustc -vV` (host should end in `windows-msvc`), `node -v` and `pnpm -v`.
- Keep the repo on a local drive, **not** inside OneDrive. OneDrive syncing `target/` and `node_modules/` makes builds slow and flaky.
- The first `cargo build` takes several minutes, because Tauri has many dependencies. Later builds are incremental.
- Windows Defender can slow builds a lot. Optionally add the repo folder as an exclusion in Windows Security → Virus & threat protection → Exclusions.
- **HEIC and AVIF need `grape-heif.exe`** (D33, D41). It isn't fetched: take it from a CI run (the `grape-heif-x86_64-pc-windows-msvc` artifact) or build it with `.\tools\grape-heif\build.ps1 -Install`, then pass the Windows sidecars overlay, which needs FFmpeg and bsdtar in `binaries\` too. "grape-heif (HEIC and AVIF)" below has both ways. Without it, a HEIC or AVIF drop says the image helper is missing; nothing else needs it. **Replace one from before D41:** a `grape-heif.exe` built for D33 (`1.23.7-grape.1`, `protocol=1` on the second line of its `-hide_banner -version`) speaks protocol 1, so with this Grape every HEIC and AVIF drop, HEIC ones that worked before included, says "Grape's image helper doesn't match this version of Grape.". `pnpm tauri build` refuses it (the bundling gate), but `pnpm tauri dev` doesn't run the gate, so build it again or take CI's artifact before testing D41.

## Running a CI build

To try Grape without the dev setup above, install the build CI makes on every run. It's a release build, unsigned until M7.

Before uploading it, CI installs it silently on its Windows runner, runs the sidecars and Grape's SVG and PDF workers from the install folder, starts Grape, checks setup's log lines and that a second launch hands over to the first, then uninstalls it (`ci.yml` → `build-windows`). So a build that won't start turns CI red, and the run's log says why. The installer is still uploaded when the build and its content checks passed, so a check that trips on the runner rather than on Grape leaves something to try (since 2026-10-28; green on GitHub since `92cd1b2`).

A released version comes from GitHub Releases instead, as `Grape-Setup-x64.exe` (README → "Install", and "Releasing" below). The steps are the same. A CI build is for a commit that isn't released yet.

1. Open the run on GitHub (Actions → CI → the run for the commit). Under **Artifacts**, download `Grape-Windows-x64` and unzip it.
2. Run `Grape_<version>_x64-setup.exe`. It installs for your user only, so no admin prompt.
3. SmartScreen says "Windows protected your PC". Click **More info**, then **Run anyway**.
4. Grape starts in the notification area (it may be under the ^ overflow arrow). As a release build, its first launch also turns on launch at login (D19); turn that off in Settings if you don't want it.
5. To remove it: Settings → Apps → Installed apps → Grape → Uninstall. Your settings stay in `%APPDATA%\io.github.sussyswimmer.grape\`.

The installer is made by Tauri's NSIS bundler. If WebView2 is missing (rare on Windows 10, never on Windows 11), the installer fetches it; Grape itself still makes no network calls.

## Detecting a file drag

Windows has no system-wide "drag in progress" signal, and the dragged data object is only visible to a window the cursor enters. So detection is a **heuristic**, and the overlay is what learns the file list.

1. **Low-level mouse hook** (`SetWindowsHookExW(WH_MOUSE_LL)`) on a dedicated thread **that pumps messages** (`GetMessageW` loop). A hook thread that doesn't pump freezes the whole system's mouse.
   - `WM_LBUTTONDOWN` records the start point.
   - `WM_MOUSEMOVE` with the button down past `SM_CXDRAG`/`SM_CYDRAG` → candidate drag.
   - `WM_LBUTTONUP` → `Ended`.
   - Keep the hook callback tiny: post to a channel and return `CallNextHookEx` immediately. Windows silently removes hooks that exceed `LowLevelHooksTimeout`.
   - **[Grape, M1]** The callback only forwards presses, releases and moves-while-pressed to a worker thread. The worker does everything slower: the allowlist check below (`WindowFromPoint` can wait on another app's window), the drag threshold and the key polling. A missed release is caught by polling the mouse buttons, after three "up" readings in a row.
2. **Modifiers:** `GetAsyncKeyState(VK_SHIFT / VK_CONTROL / VK_MENU)` polled at ~120 Hz while a candidate drag is live. This avoids a keyboard hook entirely. Add `WH_KEYBOARD_LL` only if polling misses fast taps in testing.
3. **Is it a *file* drag?** Unknown until the overlay gets `DragDropEvent::Enter { paths }`.
   - **[Grape]** Reduce false positives: only arm when the window under the cursor at mouse-down (`WindowFromPoint` → `GetAncestor(GA_ROOT)` → class name) is Explorer (`CabinetWClass`, `ExploreWClass`) or the desktop (`Progman`, `WorkerW`), **or** the user enabled "Any app" in Settings.
   - If the overlay shows but `Enter` brings no paths within 300 ms of the next cursor movement, hide it.
4. **Tap trigger:** in Explorer, holding Shift while dropping switches the drag to *move* and Ctrl to *copy*. Grape opens on the key going **down**. The drop then happens on Grape's overlay, so Explorer's effect choice no longer matters (see the next section). A key already held when the drag starts doesn't open a wheel (DECISIONS D14).
5. **Esc** is polled with `GetAsyncKeyState` too. Explorer cancels its own drag when Esc is pressed (OLE's `QueryContinueDrag`), so on Windows Esc hides the wheel *and* ends the drag.

## The drop must never move the source

Explorer's source-side behaviour depends on the drop effect the target reports. With Shift held, the user's intent looks like "move". If a target returns `DROPEFFECT_MOVE` and doesn't handle the move itself, Explorer can **delete the source** ("optimized move" / `CFSTR_PERFORMEDDROPEFFECT`).

- **M1 finding:** wry 0.57's drop handler returns `DROPEFFECT_COPY` from `DragEnter` and `DragOver`, but never sets the effect in `Drop`, and leaves it unset for drags without files. So Grape registers its own `IDropTarget` on the overlay HWND and all its child windows (`grape_platform::windows::install_drop_target`, DECISIONS D13). It reports `DROPEFFECT_COPY` for file drags and `DROPEFFECT_NONE` otherwise, in every callback. CI checks this with the shell's own data object and Shift, Ctrl and Alt held. The manual 10× test on the PC still applies.
- **The drag-source side (the float shelf, D21).** When Grape is the source, it never offers a move. A drag out of the shelf allows `DROPEFFECT_COPY | DROPEFFECT_LINK` only, so OLE turns a target's move into nothing, and a CI test checks that the allowed effects have no move bit. The data object is Grape's own `IDataObject`: it serves `CF_HDROP` and `Preferred DropEffect` = copy itself, and refuses the shell ID list formats (`CFSTR_SHELLIDLIST` and `CFSTR_SHELLIDLISTOFFSET`) as a second guard. A CI test checks that `QueryGetData` for `CFSTR_SHELLIDLIST` fails. An empty `SHCreateDataObject` with those two formats set on it won't do: on real Windows it answers `CFSTR_SHELLIDLIST` anyway, as CI showed. ReactOS's clean-room Recycle Bin target deletes the files of any drop with a shell ID list itself, in `Drop`, without looking at the allowed effects, and with Shift held the delete is permanent. Windows' own OLE layer and Recycle Bin are closed source, so dropping a shelf item on the Recycle Bin, plain and with Shift, is the first Float check on the PC.
- This is golden rule 2, and it's the single most important Windows test.

## Overlay window
- Tauri window as described in `ARCHITECTURE.md`, plus `WS_EX_TOOLWINDOW` (no taskbar or Alt-Tab), `WS_EX_NOACTIVATE`, and `HWND_TOPMOST`.
- Size it to the monitor under the cursor using `MonitorFromPoint` + `GetMonitorInfoW` (`rcWork` for clamping, `rcMonitor` for size).
- Per-monitor DPI v2: Tauri already declares it. Convert hook coordinates (physical) consistently and test mixed 100%/150% setups.
- **UIPI:** drags from an *elevated* app (e.g. an admin Explorer window) can't drop onto a non-elevated Grape. That's expected; document it and don't try to run Grape elevated.

## Sound
No haptics on Windows. The tick plays via WebAudio in the overlay or `PlaySoundW` with `SND_ASYNC | SND_MEMORY` on a preloaded WAV.

## File actions
- Share: the share sheet, through `IDataTransferManagerInterop::ShowShareUIForWindow` (D21). Nearby Share appears in it if the user turned it on.
  - Files only. Folders, missing items and shortcuts (`.lnk`, `.url`, `.wsh`, which `StorageFile` can't represent) are left out, and a toast says so. A `\\?\` prefix is stripped first.
  - On the action's thread, in the multithreaded apartment, each file is looked up with `StorageFile::GetFileFromPathAsync`, all at once, with 10 s for the lot. A file that fails or is late is left out too. Each one is kept as an agile reference so it can cross threads. Grape keeps the multithreaded apartment for the app's life (`CoIncrementMTAUsage`, once), so it isn't torn down under the files the sheet's package still holds.
  - The sheet belongs to an anchor window on a thread of its own, "grape-share": a single-threaded apartment with a message loop, started on first use and kept for the app's life. The anchor is a 32 × 32 logical px `WS_POPUP` centered where the wheel was, `WS_EX_TOOLWINDOW | WS_EX_LAYERED | WS_EX_TRANSPARENT` at alpha 1 of 255: no taskbar button or Alt-Tab entry, invisible and click-through. It isn't topmost and isn't `WS_EX_NOACTIVATE`, and it's shown with `SW_SHOWNOACTIVATE`, so Grape never takes the focus to open the sheet.
  - The `DataRequested` handler sets a title (the file's name, or "{n} files"; never empty), `DataPackageOperation::Copy` and the files read-only (`SetStorageItems(…, true)`). It calls `FailWithDisplayText` if any of that fails, and always returns `Ok`. It's removed as Chromium does it: right after the call when it already ran inside it or the call failed, otherwise at the start of the handler, and never inside a synchronous call.
  - If the handler hasn't run 30 s after the call (Chromium's limit), Share fails with a "Couldn't share" toast, and the handler is removed.
  - When the sheet closes and activates the anchor (once it has asked for the files, whether they filled or not), the anchor hands the foreground back to the window that had it when the share began, unless that one is gone or Grape's, and then hides. It hands it back first, while the anchor is still the active window, so Grape may still set the foreground.
  - Every HRESULT on the way goes to the log (`share: …`), because which windows the sheet accepts isn't documented anywhere.
- Float: the shelf is a webview window that `float.rs` builds on first use. `grape_platform::windows::show_shelf` shows, moves and resizes it with `SetWindowPos(HWND_TOPMOST, …, SWP_NOACTIVATE | SWP_SHOWWINDOW)`, and `hide_shelf` hides it, on the main thread. Never use Tauri's `show`, `hide` or `set_focus` on it.
  - `harden_shelf` uses the overlay's subclass (D11) with other bits: `WS_EX_TOOLWINDOW` on (no taskbar button, not in Alt-Tab), `WS_EX_APPWINDOW` and `WS_EX_NOACTIVATE` off, and nothing added to position changes. So the shelf is activatable: a click on it activates Grape. The drag out needs that, because only the foreground window can capture the mouse.
  - It refuses drops (`refuse_drops`, D13) at creation and before every show, so a drag out of it dropped back on it does nothing.
  - It can't be minimized or maximized (`minimizable(false)`, `maximizable(false)`). Once a click has made it the active window the window keys reach it, and a minimized tool window has no taskbar button to come back from. A shelf minimized anyway counts as closed, so the next Float places it again, and `show_shelf` first restores it with `ShowWindow(SW_SHOWNOACTIVATE)`. The snap leaves a minimized shelf alone.
  - A close request (Alt+F4 on the active shelf) is the header's ×: `float::on_window_event` calls `prevent_close`, then empties and hides the shelf off the main thread. The window is never destroyed with its items kept.
  - Double-click or Enter reveals an item (`explorer.exe /select`). An item that's gone reveals nothing, because Explorer would open some other folder instead: the page doesn't ask for a row marked Missing, and `float_reveal` checks again (the page's view can be stale), logs it and sends a fresh view.
  - **Drag out** (`grape_platform::windows::drag_out`): `SHDoDragDrop` with the shell's own drop source and generic drag image, offering copy or link only, never move. The data object is Grape's own `IDataObject` (`ShelfData`). It serves two formats itself, each `GetData` a fresh `HGLOBAL` copy, and neither can be replaced: `CF_HDROP` (the block Copy puts on the clipboard), which has no common-parent rule, so files from several folders work, and `Preferred DropEffect` = copy. It never serves or stores a shell ID list (`Shell IDList Array`, `Shell Object Offsets`): asked for one, it fails with `DV_E_FORMATETC`, whatever anyone tried to store, and a CI test checks that `QueryGetData` for `CFSTR_SHELLIDLIST` fails. Every other format a caller stores with `SetData` (the drag image, a target's `Performed DropEffect`, a drop description) is kept in an inner, empty `SHCreateDataObject`, and only formats stored that way are served back or listed, since that object makes up formats of its own even when empty. If looking at the items before the drag takes over a second (a share that stopped answering), no drag starts: the press that asked for it may be over.
  - It runs on the main thread, which owns the window and OLE. The `float_drag_out` command is async and queues it there, because a synchronous command would run the drag loop inside WebView2's IPC callback.
  - `float_drag_out` first leaves out the items that are gone, on its own thread, so a share that stopped answering never stalls the main thread while the button is held. With none left, no drag is queued and their rows turn Missing.
  - Then, before the drag, `drag_out` checks that the calling thread owns the window, that a mouse button is still down (otherwise nothing starts: the drag would drop at once wherever the pointer is), that the paths are absolute and still there, and that no other drag out is running. It reads the button once more after the paths have been looked at, just before the drag starts, in case it came up meanwhile.
  - The result says copied, linked or cancelled. Some targets don't report what they did, so it's only logged.
  - **Watchdog:** during the drag a thread reads the buttons every 100 ms. Once no button has been down for 3 s, it posts Esc (`WM_KEYDOWN` and `WM_KEYUP`, `VK_ESCAPE`) to the window holding the drag thread's mouse capture (`GetGUIThreadInfo`), once, and logs it. If no window holds the capture, it posts the same Esc to the drag thread itself (`PostThreadMessageW`) instead. That ends a drag that missed the release, which would otherwise hold up the whole app.
- Tool panel (D31): the `panel` window is declared hidden in `tauri.conf.json` (`focusable: true`, `focus: false`, `acceptFirstMouse`) and hardened in setup with `harden_panel` (the shelf's bits: a tool window that a click activates) and `refuse_drops` (D13), again before every show.
  - `grape_platform::windows::show_panel` shows and moves it with `SetWindowPos(HWND_TOPMOST, …, SWP_NOACTIVATE | SWP_SHOWWINDOW)`, and `hide_panel` hides it, on the main thread. Never Tauri's `show` or `set_focus`: tao's `set_focus` falls back to a synthetic Alt press, which is Grape's Actions key and opens Explorer's menus. Never `SetForegroundWindow` on the panel, `AttachThreadInput`, synthetic keys or a global hotkey. A drop target doesn't get "the last input event", so Windows wouldn't give Grape the foreground anyway.
  - The first click activates it (`MA_ACTIVATE`) and should reach the control under it; whether it does through WebView2's child window, of another process, is a PC check. Until then Explorer keeps the keyboard, and the page says "Click here to use the keyboard."
  - **Esc poll:** while a panel is open, "grape-panel-esc" reads `GetAsyncKeyState(VK_ESCAPE)` every 30 ms (`escape_down`) and closes the panel on a press made with no mouse button down, but only until the panel's window first has the focus (its `WindowEvent::Focused(true)`; a panel that replaces one with the focus counts as focused). After that the page handles Esc while it has the keyboard, and an Esc pressed in another app (a rename in Explorer, a menu, a dialog) is that app's: the poll leaves the panel alone. It never consumes the key: the app in front gets it too. An Esc with a button down, in this sample or the one before, belongs to a drag (the next wheel's, or the page's reorder) and is skipped: OLE ends a drag on the Esc key-down, so the button may come up before the next sample (`panel::model::EscPoll`).
  - **The page's Esc:** `panel_cancel` is refused while a mouse button is down (`primary_button_down`), for the same reason, and the page takes input again.
  - **Hand-back:** when it shows, the panel records the foreground window if it's another app's (`other_app_foreground`). On close, if the panel is the foreground window, `hide_panel` calls `SetForegroundWindow` on that window first, while Grape may still set the foreground, then hides; the result (`HandBack`) goes to the log. The decision is `win_rules::hand_back_plan`, tested on every OS: only a panel in front hands anything back, and only to a live window of another app (never the panel or another of Grape's windows).
  - The overlay is raised to the top of the topmost band on every show (`raise_topmost`, `SetWindowPos(HWND_TOPMOST, …, SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE)`, queued on the main thread right after the show), so an open panel or shelf, topmost too, never covers a wheel.
  - In the same main-thread call, `reframe_overlay` reads the overlay's rect back (`GetWindowRect`) and, while it isn't the monitor's frame, sets it again with `SetWindowPos(HWND_TOPMOST, frame, SWP_NOACTIVATE)`, at most three times (`win_rules::reframe`, tested on every OS), then logs the rect in physical pixels, with a warning if it's still off: a resize or a show onto a monitor with another scale can make tao rescale the window in its `WM_DPICHANGED` handler, which would leave the wheel drawn off the window and part of the monitor outside Grape's drop target. Whether Windows sends that message to the hidden overlay at the move or only at the show is a PC check (`TESTING.md` → Drag + wheel).
- Copy: `CF_HDROP` + `Preferred DropEffect = DROPEFFECT_COPY` on the clipboard, so pasting in Explorer copies. Grape writes both with `SetClipboardData` from a message-only window it makes for the call, because `SetClipboardData` fails when the clipboard has no owner. The data is plain memory, not delayed rendering, so it stays after the window is gone, and there's no OLE data object to keep alive or flush.
- Move: `IFileOpenDialog` with `FOS_PICKFOLDERS`, titled "Move {name} to…" or "Move {n} items to…", starting in the first item's folder. After a drop Grape has no right to the foreground (the drop is Explorer's input), so the picker is owned by an invisible window of the move thread's own: a 1 × 1 `WS_POPUP` with `WS_EX_TOPMOST | WS_EX_TOOLWINDOW` at the middle of the work area under the cursor, never shown, destroyed once the move is done. A window owned by a topmost window is topmost, so the picker can open in front of Explorer, inactive until clicked (a PC check: `TESTING.md` → File actions); Grape never calls `SetForegroundWindow` or makes up input. Settings' picker keeps the Settings window as its owner. Then `IFileOperation::MoveItem` with `FOF_ALLOWUNDO | FOFX_ADDUNDORECORD`, so the shell shows its own progress and name-clash questions, owned by the same invisible window (`SetOwnerWindow`), so they open in front as the picker does (a PC check too). Whether Ctrl+Z in Explorer undoes a move made by another process is still to check on the PC. Items already in the picked folder are skipped. If any item may be on another volume than the folder, a Yes/No box asks first, with No as the default. Two checks feed that, and either is enough: the volume path (`GetVolumePathNameW`), and the volume serial number of each folder once junctions, symlinks and DFS links are followed (`GetFileInformationByHandle`). A volume that can't be read counts as another one. Everything runs on a thread of its own in a single-threaded COM apartment.
  - **The topmost picker's costs**, PC checks too (`TESTING.md` → File actions): an owned window gets no taskbar button; a toast already on screen where the picker opens can stay under it until it hides; and when the picker closes, Windows can't activate its hidden owner, so it may activate the next window down from the picker, which is another always-on-top window (Task Manager kept on top, a pinned video) if one is showing, not Explorer. If QA sees that, drop the owner, and with it the picker, to the top of the normal band on the picker's first `IFileDialogEvents::OnFolderChange` (`SetWindowPos(owner, HWND_NOTOPMOST, …, SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE)`). The price: once the user clicks Explorer, the picker can go behind it with no taskbar button to bring it back.
  - What moved is read back from the disk: an item moved only if its old path is gone while its old folder can still be read. A progress sink (`IFileOperationProgressSink::PostMoveItem`) supplies hints: where each item went, which matters after a "keep both" rename, and whether anything inside a folder moved. A folder still in its old place after a merge, a skip inside it or a cancel, and an item whose old place can't be read any more, are reported as unsure. The toast then says "Some of it may not have moved" and shows the destination, never "moved" or "stayed put".
  - Clicking the toast runs `explorer.exe /select,"<path>"` with the quotes written out (`raw_arg`). `Command::arg` would quote the whole switch when the path has a space and leave a comma bare.
- Copy Path: `CF_UNICODETEXT`, paths joined with `\r\n`.
- Terminal: with the default "Windows Terminal" setting, `wt.exe -d "<dir>"` if `wt` starts; otherwise, or when the user chose PowerShell in Settings, `powershell.exe -NoExit -Command "Set-Location -LiteralPath '<dir>'"` in a new console. PowerShell reads `'`, `‘`, `’`, `‚` and `‛` as the same quote, so each one in the path is doubled. wt splits its command line at `;`, so a path with `;` goes straight to PowerShell. Files open their parent folder.

## Conversions that use Windows components
- **HEIC and AVIF, both ways:** `grape-heif.exe`, Grape's own image helper (DECISIONS D33, D41; "grape-heif (HEIC and AVIF)" below). It links libheif with libde265 (HEIC decode), x265 (HEIC encode), dav1d (AVIF decode) and libaom's encoder (AVIF encode) statically, so it needs no Store HEIF, HEVC or AV1 extension. x265 makes it GPL-3.0-or-later as a whole, which is fine because Grape is free and open source and it's a separate executable (`ENGINES.md` licensing rules); its texts are in `licenses\grape-heif\` and every release carries its source bundle. Grape runs it in a Job Object (2 GiB, ended with Grape, one process), with no console and without `LIBHEIF_PLUGIN_PATH` or `LIBHEIF_SECURITY_LIMITS`.
- **H.264 encode:** the FFmpeg sidecar with libx264, allowed under the same rules. Prefer `h264_mf` / `h264_nvenc` / `h264_qsv` / `h264_amf` hardware encoders when present, with x264 as the fallback.

## Sidecars

**The lock's builds are for dev testing only.** The prebuilt FFmpeg builds the lock pins today are never bundled: the installer carries Grape's own minimal FFmpeg, which CI builds (DECISIONS D24, lane B's `scripts/ffmpeg/build.sh`), and the lock will point at Grape's own release at M7 (D25).

FFmpeg and ffprobe are separate programs that Grape runs (golden rule 6). They aren't in the repo. A script fetches the builds pinned in `scripts/sidecars.lock` (D25; the pin itself is D22). Run it from the repo root:

```powershell
.\scripts\fetch-sidecars.ps1          # fetch, unless they're already current
.\scripts\fetch-sidecars.ps1 -Force   # fetch again anyway
```

- It works in Windows PowerShell 5.1 and PowerShell 7. If PowerShell says running scripts is disabled on this system, run `powershell -ExecutionPolicy Bypass -File .\scripts\fetch-sidecars.ps1` instead. That changes no setting.
- **What lands where.** `apps/desktop/src-tauri/binaries/`, which git ignores, gets:
  - `ffmpeg-x86_64-pc-windows-msvc.exe` and `ffprobe-x86_64-pc-windows-msvc.exe`, the target-triple names Tauri's `bundle.externalBin` looks for. Both come from one BtbN zip (194 MB).
  - `ffmpeg-LICENSE.txt`, the build's GPLv3 text from that zip: a dev reference only, never bundled. The script never writes into `licenses/`, which is committed and written by hand (`licenses/README.md`).
  - `sidecars.stamp`, written last: the lock's SHA-256, the target, and each file's SHA-256.
- **The checks.** The zip downloads into a new temp folder over HTTPS (TLS 1.2 or later). Its size and SHA-256 must match the lock before anything is extracted. On a mismatch it's deleted and nothing changes. Only the files the lock names are extracted. Each program then runs with `-hide_banner -version`: the first line must name the lock's version, and the configuration line must not have `--enable-nonfree`. Only after every check passes do the files replace the ones in `binaries/`. The temp folder is always deleted.
- **A second run** reads the stamp. If the lock, the target and every file still match, it says the sidecars are already current and stops. If anything differs (a new lock, a changed or missing file), it fetches again.
- It doesn't change `PATH` or install anything. This script is the only download, at build time. Grape itself never downloads anything (golden rule 3).
- **CI** runs it in the Sidecars job: in Windows PowerShell 5.1, then again in PowerShell 7, which must find them current. `binaries/` is cached by the hashes of the lock and both fetch scripts, so a changed script runs in full. The job lists the files and their sizes, and builds nothing.
- **In the installer.** `apps/desktop/src-tauri/tauri.sidecars.windows.conf.json` adds both, Grape's bsdtar ("bsdtar (RAR)", below) and `grape-heif` ("grape-heif (HEIC and AVIF)", below) to `bundle.externalBin` for a build that passes it (from `apps\desktop`), with `licenses/ffmpeg/`, `licenses/libarchive/` and `licenses/grape-heif/`. It's the one Windows overlay that sets `externalBin`: a second one would replace its list, not add to it. Before the build it runs the gate, `scripts/check-sidecars.mjs` (D25), on the merged list in `TAURI_CONFIG`. The gate refuses anything but Grape's own FFmpeg build (its version line ends in `-grape`, D24) with `licenses/ffmpeg/` (the license texts, and `SOURCE.md` with the source link) and its `THIRD_PARTY_NOTICES.md` section, anything but Grape's own bsdtar with `licenses/libarchive/` and its section (D27), and anything but Grape's own grape-heif speaking this Grape's image helper protocol, with `licenses/grape-heif/` and its section (D33, D41). So the lock's BtbN build works for `tauri dev` only. The installer carries FFmpeg now that CI builds it (D24): CI's `ffmpeg` workflow cross-compiles `ffmpeg.exe` and `ffprobe.exe` on `ubuntu-24.04` with `scripts/ffmpeg/build.sh windows-x86_64` and runs them on `windows-latest` (the script can't run them on Linux), and CI's installer job and `release.yml` take them from the same run, put them in `binaries\` with bsdtar and grape-heif, and build with `--config src-tauri/tauri.pdfium.windows.conf.json --config src-tauri/tauri.sidecars.windows.conf.json`. The complete source, `grape-ffmpeg-sources.tar`, is the same run's artifact and goes on the draft release.
- **In dev**, `pnpm tauri dev --config src-tauri/tauri.sidecars.windows.conf.json` makes tauri-build copy them into `target\debug` as `ffmpeg.exe` and `ffprobe.exe`, next to Grape's executable, with `bsdtar.exe` and `grape-heif.exe`. tauri-build fails the build if any file the overlay lists is missing from `binaries\`, and this script brings only FFmpeg, so put a bsdtar and a grape-heif there first, even to test only FFmpeg: `.\scripts\bsdtar\build.ps1 -Install` and `.\tools\grape-heif\build.ps1 … -Install`, or CI's artifacts ("bsdtar (RAR)" and "grape-heif (HEIC and AVIF)", below). `tauri dev` doesn't run the gate, so the lock's FFmpeg works there. To test the FFmpeg the installer ships, download the `ffmpeg-x86_64-pc-windows-msvc` artifact from a CI run (the `ffmpeg` workflow): its `ffmpeg-x86_64-pc-windows-msvc.exe` and `ffprobe-x86_64-pc-windows-msvc.exe` go in `binaries\` as they are, and it holds `BUILDINFO.txt`, `SHA256SUMS` and `licenses\ffmpeg\` too. The same run's `ffmpeg-source` artifact is its complete source. Without the overlay none of them are copied there.
- **Installed**, they lose the suffix: the installer puts `ffmpeg.exe` and `ffprobe.exe` next to `Grape.exe` in `%LOCALAPPDATA%\Grape`, with `licenses\ffmpeg\`. That's where `src/sidecars.rs` looks, never on `PATH`. Without either one an audio or video drop says "Grape's media converter is missing" / "Reinstalling Grape brings it back.", and the log's `sidecars:` line says which is missing (D35).
- `GRAPE_SIDECARS_NO_RUN=1` skips the `-version` runs and writes no stamp, so the download can be tested on another OS. It's for testing only. The next run without it checks everything again.
- **Not grape-heif.** The image helper for HEIC and AVIF isn't in `sidecars.lock` and this script never fetches it: CI builds it from `tools\grape-heif` (D33, "grape-heif (HEIC and AVIF)" below), until M7 publishes it with the releases.

## PDFium

PDFium is the library Grape reads PDFs with (DECISIONS D29). Every installer and DMG carries it, as they carry FFmpeg. It isn't in the repo either: the same script fetches it, as pinned in `scripts/sidecars.lock` → `libraries`. A plain run fetches it with the sidecars; `-Only pdfium` fetches just it (3.9 MB):

```powershell
.\scripts\fetch-sidecars.ps1 -Only pdfium
```

- **What lands where.** `apps\desktop\src-tauri\binaries\pdfium-x86_64-pc-windows-msvc.dll` (7.5 MB), from bblanchon's `pdfium-win-x64.tgz` for `chromium/8086`. The script extracts it with Windows' own `%SystemRoot%\System32\tar.exe` (Windows 10 1803 and later have it), never a `tar` on `PATH`. It gets its line in `sidecars.stamp`, and with `-Only` the other files keep theirs.
- **The checks.** The archive's size and SHA-256 must match the lock, and then the DLL's own SHA-256 too. A DLL can't be run, so there's no `-version` check.
- **In the installer.** A build that passes `--config src-tauri/tauri.pdfium.windows.conf.json` (from `apps\desktop`) installs it as `pdfium.dll` next to `Grape.exe` in `%LOCALAPPDATA%\Grape`, with its license texts in `licenses\pdfium\`. CI's installer job does, with the Windows sidecars overlay after it ("Sidecars", above): `pnpm tauri build --bundles nsis --ci --config src-tauri/tauri.pdfium.windows.conf.json --config src-tauri/tauri.sidecars.windows.conf.json`. A build or `tauri dev` run without it has no PDFium, so a PDF drop says "Grape's PDF library is missing" / "Reinstalling Grape brings it back." (D35; in dev, that means passing this overlay). In dev that holds only until a run with the overlay: tauri-build leaves `target\debug\pdfium.dll` behind, and later plain runs find it. Delete it to see the toast. The overlay fails the build while the DLL isn't fetched.
- **In dev**, `pnpm tauri dev --config src-tauri/tauri.pdfium.windows.conf.json` makes tauri-build copy it to `target\debug\pdfium.dll`, next to Grape's executable. Pass `--config` twice to add `tauri.sidecars.windows.conf.json` too, which needs FFmpeg, bsdtar and grape-heif in `binaries\` ("Sidecars", above).
- **Who loads it.** Only the PDF worker: Grape's own executable started again as `Grape.exe --grape-pdf-worker`, once per PDF job, with no window. It loads `pdfium.dll` from next to the executable by its full path, never from `PATH` or the system folders. Grape's main process never loads it, so a crash on a bad PDF ends only that job.
- **Tests.** `cargo test -p grape-engines --features pdf-it` runs the tests that need PDFium. They fail, not skip, without `GRAPE_TEST_PDFIUM`, the DLL's full path: `$env:GRAPE_TEST_PDFIUM = "$PWD\apps\desktop\src-tauri\binaries\pdfium-x86_64-pc-windows-msvc.dll"` from the repo root. CI's Rust job runs them after fetching PDFium only.
- From M7, the bundler signs the DLL in place in `binaries\` when it signs the installer. That changes its hash, so the next fetch run downloads it again.

## bsdtar (RAR)

Grape reads RAR archives with `bsdtar`, a separate program it builds from libarchive 3.8.10 and its own patches (DECISIONS D27). It isn't in the repo or in `scripts/sidecars.lock`: build it on the PC, from the repo root:

```powershell
.\scripts\bsdtar\build.ps1 -Install
```

- **What it needs:** git, and the Dev setup's Build Tools: the C++ workload with its recommended components brings MSVC, CMake and the Windows SDK (`mt.exe`). It finds them through `vswhere` and never changes `PATH`. It works in Windows PowerShell 5.1 and PowerShell 7; if PowerShell says running scripts is disabled, run `powershell -ExecutionPolicy Bypass -File .\scripts\bsdtar\build.ps1 -Install`. It downloads only libarchive's release tarball (9.3 MB) and checks its size and SHA-256 before anything is extracted. A build takes a few minutes.
- **What lands where.** `target\bsdtar\out\bsdtar-x86_64-pc-windows-msvc.exe`, with `BUILDINFO.txt` and `SHA256SUMS`; `-Install` copies it into `apps\desktop\src-tauri\binaries\`. The tarball stays in `target\bsdtar\dl\`, and the extract and build tree (`target\bsdtar\work\`) are deleted at the end. Before it reports success it checks that bsdtar imports only `KERNEL32`, `ADVAPI32` and `bcrypt` (the C runtime is linked in), that its manifest has `activeCodePage` UTF-8 and `longPathAware`, that its version line is exactly `bsdtar 3.8.10-grape.1 - libarchive 3.8.10 libb2/bundled `, and that `licenses\libarchive\copyright-lines.txt` still matches the source. `-CheckOnly` runs the checks again on what `out\` holds.
- **Or take CI's build:** download the `bsdtar-x86_64-pc-windows-msvc` artifact from a CI run (the `bsdtar` workflow) and put the `.exe` in `apps\desktop\src-tauri\binaries\`.
- **In dev**, `pnpm tauri dev --config src-tauri/tauri.sidecars.windows.conf.json` (from `apps\desktop`) makes tauri-build copy it to `target\debug\bsdtar.exe`. That overlay lists FFmpeg, ffprobe and grape-heif too, so run `.\scripts\fetch-sidecars.ps1` for the dev FFmpeg and put a grape-heif in `binaries\` first ("grape-heif (HEIC and AVIF)", below).
- **Tests.** `$env:GRAPE_TEST_BSDTAR = "$PWD\target\bsdtar\out\bsdtar-x86_64-pc-windows-msvc.exe"; cargo test -p grape-engines --features rar-it --lib archive::rar` runs the RAR tests against the real bsdtar. They fail, not skip, without the variable. CI runs them against the bsdtar it built in the same run.
- **In the installer.** It ships in `tauri.sidecars.windows.conf.json` with FFmpeg: CI's installer job and `release.yml` take it from the same run's `bsdtar` workflow. Installed, it's `bsdtar.exe` next to `Grape.exe`, with `licenses\libarchive\`, where Grape looks for it, never on `PATH`. Without it a RAR drop says "Grape's RAR helper is missing" / "Reinstalling Grape brings it back.", and the log's `sidecars:` line says bsdtar is missing (D35).
- **How Grape runs it.** Only as `bsdtar -c -P -f - --format pax @-`: Grape writes the RAR into its stdin and reads a tar from its stdout; bsdtar never writes a file. It runs in a new, empty folder in `%TEMP%` (`grape-bsdtar-…`, removed afterwards), with a cleared environment (`PATH` set to that folder, `TZ=UTC0`, `TAR_READER_OPTIONS=rar:hdrcharset=UTF-8` and `SystemRoot`), and with `CREATE_NO_WINDOW`, so no console window opens.
- **Defender** may look at an unsigned `bsdtar.exe` the first time it runs, which can make the first RAR slower. It's signed with the installer from M7. Manual QA checks it (`TESTING.md` → "RAR, M3").

## grape-heif (HEIC and AVIF)

Grape converts HEIC and AVIF to and from JPG, PNG, WEBP, TIFF and BMP, and into each other, with `grape-heif.exe`, a small program of its own in `tools\grape-heif` (DECISIONS D33, D41). It's built on libheif 1.23.7 with libde265 1.1.3 and x265 4.3 for HEIC, and dav1d 1.5.4 and libaom 3.15.2 (its encoder only) for AVIF, which vcpkg builds at a pinned commit and which are linked statically, with libheif's plugin loading compiled out. It isn't in `scripts/sidecars.lock`: CI builds it, or you build it on the PC, from the repo root:

```powershell
.\tools\grape-heif\build.ps1 -VcpkgRoot C:\gh-vcpkg -BinaryCache C:\gh-vcpkg-cache -Install
```

- **What it needs:** git, Rust (the Dev setup) and the Build Tools' C++ workload; vcpkg fetches its own CMake, NASM, ninja and pkgconf, and Strawberry Perl (libaom's build, about 300 MB to download) and Python and meson (dav1d's). The first build takes about 45 to 50 minutes and about 5 GB, mostly x265 and libaom (an estimate until CI has timed it); `-BinaryCache` makes later ones quick. Keep `-VcpkgRoot` short (vcpkg's build trees are deep); without it vcpkg goes in `target\grape-heif\vcpkg`. It works in Windows PowerShell 5.1 and PowerShell 7 (`powershell -ExecutionPolicy Bypass -File …` if scripts are disabled).
- **What it does:** clones vcpkg at the commit in `tools\grape-heif\vcpkg.lock.json` (never a vcpkg already on the PC), downloads the five source archives first and checks each SHA-512 against the lock and the port, builds `libheif[core,hevc,aom,dav1d]:x64-windows-static` with Grape's two overlay ports (libheif and aom), then `cargo build --release --locked` in `tools\grape-heif` with the static C runtime.
- **What lands where.** `tools\grape-heif\target\out\grape-heif.exe`, with `BUILDINFO.txt` (the banner, the pins, the Visual Studio, compiler, CMake, NASM, ninja, Perl, Python, meson and Rust versions) and `SHA256SUMS`; `-Install` copies it to `apps\desktop\src-tauri\binaries\grape-heif-x86_64-pc-windows-msvc.exe`.
- **Or take CI's build:** download the `grape-heif-x86_64-pc-windows-msvc` artifact from a CI run (the `grape-heif` workflow, which CI calls on every push) and save `grape-heif.exe` as `apps\desktop\src-tauri\binaries\grape-heif-x86_64-pc-windows-msvc.exe`. The artifact also holds `BUILDINFO.txt`, `SHA256SUMS` and `licenses\grape-heif\` (the GPL and the other texts, and `SOURCE.md`, which says the complete source is the same run's `grape-heif-source` artifact). CI builds it with the newest Visual Studio on GitHub's `windows-latest` image (2026 today); its vcpkg and cargo caches are keyed on that compiler, so a runner update rebuilds once and caches again.
- **Check it:** `.\tools\grape-heif\target\out\grape-heif.exe -hide_banner -version` prints `grape-heif version 1.23.7-grape.2 …`, then `configuration: libheif=1.23.7 libde265=1.1.3 x265=4.3 dav1d=1.5.4 aom=3.15.2 plugins=disabled crt=static protocol=2`. The `protocol=` must be `PROTOCOL` in `crates/grape-heif-proto/src/lib.rs`: a helper built for another protocol refuses every job, and the bundling gate refuses it.
- **In dev**, `pnpm tauri dev --config src-tauri/tauri.sidecars.windows.conf.json` (from `apps\desktop`) makes tauri-build copy it to `target\debug\grape-heif.exe`, next to Grape's executable. That overlay lists FFmpeg, ffprobe and bsdtar too, so they must be in `binaries\` as well ("Sidecars" and "bsdtar (RAR)", above). Add `--config src-tauri/tauri.pdfium.windows.conf.json` before it for PDFs too. Never add another overlay that sets `bundle.externalBin`: its list would replace this one's.
- **In the installer.** CI's installer job and `release.yml` take it from the `grape-heif` job of the same run, check its SHA-256 and build with `--config src-tauri/tauri.pdfium.windows.conf.json --config src-tauri/tauri.sidecars.windows.conf.json`, which bundles it with FFmpeg and bsdtar. That overlay runs the gate first (`scripts/check-sidecars.mjs`, which reads the merged list from `TAURI_CONFIG`): it refuses anything but Grape's build (the banner's `-grape` marker) speaking this Grape's protocol (`protocol=N` on the banner's configuration line equal to grape-heif-proto's `PROTOCOL`, D41), and needs `licenses\grape-heif\` with `SOURCE.md` and its `THIRD_PARTY_NOTICES.md` section. Installed, it's `grape-heif.exe` next to `Grape.exe`, where `src/sidecars.rs` looks for it, never on `PATH`. Without it a HEIC or AVIF drop says "Grape's image helper is missing" / "Reinstall Grape to work with HEIC and AVIF files.", and the log's `sidecars:` line says it's missing.
- **The source.** It's GPL-3.0-or-later as a whole (x265), so every build comes with its complete source: CI's `grape-heif-source` artifact, `grape-heif-<version>-source.tar.gz`, made by `tools\grape-heif\source-bundle.sh` (Grape's code, every crate, the five archives, vcpkg's ports and both overlays, and how to build it), and the same file on the GitHub Release. `licenses\grape-heif\SOURCE.md` says what's in it.
- **Tests.** `cargo test --release --locked` in `tools\grape-heif` (with `VCPKG_ROOT` set to the vcpkg folder) runs its own tests: the banner, HEIC and AVIF round trips through libheif (alpha, ICC, sizes from 1×1, a 10-bit AVIF, a cut-off one), the encoder settings read back, plugin loading compiled out, and `LIBHEIF_SECURITY_LIMITS=off` ignored. With `$env:GRAPE_TEST_HEIF` set to the exe's full path, `cargo test -p grape-engines --features heif-it` converts real files through it (add `$env:GRAPE_TEST_HEIF_FIXTURES`, a folder of CI's `heif-fixtures` artifact), and `cargo test -p grape-platform --features heif-it --test job_object -- --nocapture` encodes a 35.6 MP image under the 2 GiB Job cap and prints the peak (with `-- --nocapture`, the engine tests print the 35.6 MP AVIF encode's and decode's peaks too). All of them fail, not skip, without their variables. CI runs them against the exe it built in the same run (`heif-it-windows`).
- **How Grape runs it.** As `grape-heif.exe --grape-heif-worker`, one image per run: one JSON request on stdin, JSON lines on stdout (`crates/grape-heif-proto`). Pixels go through a new, private `grape-heif-…` folder in `%TEMP%`, which is its working folder and is removed afterwards (if Grape is killed or crashes mid-job, at its next start); only the finished file is written into the destination folder, with Grape's usual no-overwrite rule. It starts with `DETACHED_PROCESS` (no console, so Windows starts no `conhost.exe` for it), without `LIBHEIF_PLUGIN_PATH` and `LIBHEIF_SECURITY_LIMITS`, and goes into a Job Object (`grape_platform::windows::job`) before it's given any work: 2 GiB of committed memory at most, ended when the job closes (when the conversion ends, is cancelled, or Grape exits or crashes), one process, no error dialogs, no clipboard, desktop or system settings. The last three are UI limits, which a nested job can't have: when Grape itself runs inside a job (`pnpm tauri dev` runs it through cargo, which makes one; so do some launchers), the helper starts in that job, its own job is nested under it with every other limit, and the log says `contain: Grape runs inside a job, …` once. At start it loads DLLs from System32 only and turns off Windows' error boxes. Decoding stops at 134 MP and 512 MiB of file; encoding at 35.6 MP and 16,888 pixels a side for HEIC or 16,384 for AVIF ("…is too large to save as HEIC." or "… as AVIF."). libaom encodes an AVIF on at most 8 threads at speed 6, 4:2:0, quality 50, and keeps the ICC profile.
- **Defender** may look at an unsigned `grape-heif.exe` the first time it runs, which can make the first HEIC or AVIF slower. It's signed with the installer from M7. Manual QA checks it (`TESTING.md` → "HEIC, D33" and "AVIF, D41").

## Distribution
- Installer: Tauri **NSIS** bundle (per-user install, no admin needed) plus a portable `.zip`. Keep MSI for later.
- Code signing: unsigned builds trigger SmartScreen ("Windows protected your PC"). Free option for open source: **SignPath Foundation** (free signing for OSS projects that meet its criteria). Alternatives: Azure Trusted Signing (paid, identity checks). Log in DECISIONS when chosen.
- Launch at login: `tauri-plugin-autostart` (HKCU Run key). After an uninstall that kept `settings.json` with launch at login on, the reinstalled release build sees that neither Run key has the `Grape` value (`grape_platform::windows::run_value`, read with `RegGetValueW`) and registers it again, logging "the Run value was gone (an uninstall?)". It never asks auto-launch's `is_enabled`, which is also false while Task Manager has Grape off: a value that's there, on or off, a missing one whose Task Manager record (`StartupApproved\Run`) still says off, and one naming another program are all left alone (D19). Removing the value any other way while launch at login is on (regedit, Autoruns) looks the same, so the next launch registers it again: turn it off in Settings or Task Manager. A local release build started from `target\release` in that state registers its own path, and the installed copy then leaves that value alone as another program's; turning launch at login off and on in the installed copy's Settings fixes it. Its auto-launch 0.6 writes HKLM's Run key instead when Grape runs elevated (UAC off, or the built-in Administrator; CI's runner does), and the plugin can't be told otherwise. The per-user uninstaller removes only HKCU's value, so there a "Grape" startup entry pointing at the removed exe stays until it's turned off in Task Manager → Startup apps. Known limit; a normal user's launch is never elevated (the per-user installer doesn't elevate).
- Builds: GitHub Actions `windows-latest` (x64) and `windows-11-arm` (ARM64) runners. See ROADMAP M7.

## Releasing

A version tag makes a draft release. `.github/workflows/release.yml` builds the installer and the Mac DMG from the tag and drafts a GitHub Release with them (D45). It never publishes: Maxwell checks the draft and publishes it by hand. On Windows it builds x64 only; the DMG is universal, `macos-app.yml`'s build, the same as CI's (`PLATFORM_MACOS.md` → "Releasing"). For the installer it fetches PDFium fresh (`fetch-sidecars.ps1 -Only pdfium`, every hash checked), builds Grape's own FFmpeg (`scripts/ffmpeg/build.sh`, every target, so the source bundle is compared across three builds), bsdtar and `grape-heif.exe` from the tag without any cache (their workflows), builds with the PDFium and Windows sidecars overlays, and fails if `ffmpeg.exe`, `ffprobe.exe`, `bsdtar.exe`, `grape-heif.exe`, `pdfium.dll` or any of their license folders (`licenses\ffmpeg\`, `licenses\libarchive\`, `licenses\grape-heif\`, `licenses\pdfium\`) is missing (D24, D25, D27, D29, D33).

**Cutting a release**

1. Pick the version: plain `X.Y.Z`, with no `-beta` or other suffix (the workflow refuses those tags). Set it in all four places:
   - `apps/desktop/src-tauri/tauri.conf.json` → `"version"` (the installer's version)
   - `Cargo.toml` → `[workspace.package]` → `version` (Grape's crates inherit it, except `grape-heif-proto`, whose version follows its protocol and stays as it is)
   - `apps/desktop/package.json` → `"version"`
   - `apps/desktop/ui/package.json` → `"version"`
2. Run `cargo update --workspace`. It moves Grape's own crates that inherit the version (`grape`, `grape-core`, `grape-engines`, `grape-platform`) to the new version in `Cargo.lock` and leaves every other crate alone, `grape-heif-proto` included.
3. Commit the five files (`git commit -am "Release X.Y.Z"`) and push. Wait for CI to pass on that commit.
4. Tag the commit and push that one tag:

   ```powershell
   git tag vX.Y.Z
   git push origin vX.Y.Z
   ```

   Push it by name, not with `git push --tags`. GitHub starts no workflow when more than three tags arrive in one push.

5. Open Actions → Release → the run for the tag, and wait for its jobs to finish (the version check, FFmpeg, bsdtar, grape-heif, the installer, the DMG, the draft). CI runs on the tag too.
6. Check the draft (Releases → "Grape X.Y.Z", marked Draft), following `TESTING.md` → "Release, M7" on the PC and "Release, M9" on a Mac:
   - It holds `Grape-Setup-x64.exe`, `Grape-macOS-universal.dmg`, `SHA256SUMS.txt`, the two source files, `grape-ffmpeg-windows-x64.zip` and `grape-ffmpeg-macos-universal.zip`.
   - Download `Grape-Setup-x64.exe` and `SHA256SUMS.txt` from the draft, and check the hash with the PowerShell line in the notes.
   - Install it on a clean standard user account (no admin rights), go through SmartScreen, and convert a file.
   - On a Mac, download `Grape-macOS-universal.dmg` and `SHA256SUMS.txt`, check the hash with the Terminal line in the notes, open Grape through Privacy & Security → **Open Anyway**, and convert a file.
7. Edit the draft: replace the TODO under "What's new". If the Mac checks haven't passed yet, take the Mac off the draft (D45):
   - Delete `Grape-macOS-universal.dmg` from its files.
   - In the notes, delete the `## macOS` section, the last sentence under "Offline" (it starts "On a Mac"), and the two sentences under "Source and licenses" that start "The DMG carries" and "On a Mac". The rest of the notes fits a Windows-only release.
   - `SHA256SUMS.txt` keeps the DMG's line. The notes check each file on its own, but `sha256sum -c SHA256SUMS.txt` then fails on the missing DMG; a check of every file needs `--ignore-missing`.
8. Publish it.

If the version check fails, nothing was built or released. Delete the tag (`git tag -d vX.Y.Z`, then `git push --delete origin vX.Y.Z`), fix the versions, commit and tag again. To run a tag again after a runner or network failure, use Actions → Release → Run workflow and type the tag. That button shows only once `release.yml` is on the repo's default branch. Before that, open the failed run and click **Re-run failed jobs**. A fix in the code needs a new version, because a tag stays where it is.

**What the workflow checks**
- The tag is `v` and then `X.Y.Z`, and `X.Y.Z` is the version in the four files and in `Cargo.lock`'s entries for Grape's own crates, all but `grape-heif-proto` (its version follows its protocol, and `tools/grape-heif/Cargo.lock` pins it). It prints each one and names the ones that differ. It's a job of its own that grape-heif, the installer and the DMG wait for, so a wrong tag fails in seconds, before anything builds.
- The build is the CI job's (`ci.yml` → `build-windows`): the same actions, Node 22, Rust 1.99, `pnpm install --frozen-lockfile` and `pnpm tauri build --bundles nsis --ci`. The DMG is CI's too: both call `macos-app.yml`, the release with its tag, `cache: false` and `release: true`.
- The NSIS bundler made exactly one `*-setup.exe`. It's copied to `Grape-Setup-x64.exe`, the same name in every release, and hashed into `SHA256SUMS.txt` as `<hash>  Grape-Setup-x64.exe`, in lower-case hex (the `sha256sum` format). Both files are also the run's `Grape-Setup-x64` artifact.
- **The DMG.** `macos-app.yml` with `release: true` copies the one `.dmg` Tauri made (`Grape_<version>_universal.dmg`) to `Grape-macOS-universal.dmg`, the same name in every release, and uploads it with its line in a `SHA256SUMS` file as the run's `Grape-macOS-universal-release` artifact. The release job checks that file is exactly the DMG's line and appends it to `SHA256SUMS.txt`, after the installer's: the notes' PowerShell line reads the first hash.
- The release job checks the downloaded installer against `SHA256SUMS.txt`, fills in `{{VERSION}}` and `{{HEIF_VERSION}}` in `.github/release-notes.md` (whose last paragraphs name the separate programs the installer and the DMG carry, their licenses, the two source files and the FFmpeg zips), and makes the draft with `gh release create --draft --verify-tag`.
- **The GPL sources.** The installer carries `grape-heif.exe`, `ffmpeg.exe` and `ffprobe.exe`, and the DMG `ffmpeg` and `ffprobe`, which are GPL, so the draft also gets their complete source from the same run: `grape-heif-<version>-source.tar.gz` and `grape-ffmpeg-sources.tar` (D24), each checked against its `.sha256` (FFmpeg's also against the hash the `ffmpeg` workflow reported). Both get their lines in `SHA256SUMS.txt` (GPL-3.0 section 6, GPL-2.0 section 3; D24, D33).
- **Grape's FFmpeg.** The draft also gets `grape-ffmpeg-windows-x64.zip` and `grape-ffmpeg-macos-universal.zip`: the run's two FFmpeg artifacts as they are (the programs under Tauri's names, `BUILDINFO`, `SHA256SUMS` and `licenses/ffmpeg/`), each checked against its `SHA256SUMS` and the hash the `ffmpeg` workflow reported, with the Mac programs executable again. Both get their lines in `SHA256SUMS.txt`. They're for building Grape from source (D45); pointing `scripts/sidecars.lock` at a published release's copies is lane B's step.
- **Running it again.** If the draft exists, the run replaces its files (`--clobber`) and keeps its notes, so "What's new" survives. A DMG deleted from the draft comes back. If the release is already published, the run fails and changes nothing, so a published file always matches its hash. If the Mac build fails, there's no draft at all, as when the installer fails: re-run the failed jobs.
- **Permissions.** The workflow's token is read-only. Only the release job can write (`contents: write`), and it runs no build code.
- It doesn't sign anything with a real identity (the DMG is signed ad hoc, as CI's) or add an updater, and Grape itself still makes no network calls (golden rule 3).

**Signing.** The installer and Grape are unsigned, so SmartScreen warns: "Windows protected your PC" → **More info** → **Run anyway**. The release notes say so. Signing will come from the SignPath Foundation, which is free for open-source projects (ROADMAP M7). Applying is Maxwell's step. Once it's approved, the workflow gets a signing step after the build and before the hash, so `SHA256SUMS.txt` covers the signed file, and the choice gets a DECISIONS entry.

**WebView2.** Grape's windows need Microsoft's WebView2 runtime. `tauri.conf.json` doesn't set `bundle.windows.webviewInstallMode`, so Tauri 2.12's default applies: `downloadBootstrapper`, silent (`WebviewInstallMode::default` in tauri-utils 2.10.1).
- The installer looks for WebView2 in the registry first. If it's there, nothing is downloaded.
- If it's missing, the installer downloads Microsoft's bootstrapper from `go.microsoft.com`, runs it silently, and then installs Grape. If the download fails, the install stops with an error.
- That download is the installer's, not Grape's. Windows 11 and current Windows 10 already have WebView2, so it rarely happens.
- A PC that is offline *and* has no WebView2 can't install Grape. The `offlineInstaller` mode would fix that, for about 127 MB more per download.

**Where it installs.** `%LOCALAPPDATA%\Grape`, for the current user only (`installMode: currentUser`). The folder holds Grape itself, `THIRD_PARTY_NOTICES.md` and `LICENSE.txt` (D23), and, in a build with the PDFium and Windows sidecars overlays (CI's installer and `release.yml`'s), `pdfium.dll` and `licenses\pdfium\` (D29), `ffmpeg.exe`, `ffprobe.exe` and `licenses\ffmpeg\` (D24), `bsdtar.exe` and `licenses\libarchive\` (D27), and `grape-heif.exe` and `licenses\grape-heif\` (D33, D41). The uninstaller removes that folder and the launch-at-login entry (the `Grape` value under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`). It keeps `%APPDATA%\io.github.sussyswimmer.grape\` (settings) and `%LOCALAPPDATA%\io.github.sussyswimmer.grape\` (logs and WebView2's data), unless the user ticks "Delete the application data".

## Windows QA must-checks
- Drag from Explorer, the Desktop, Downloads, search results, OneDrive placeholders (cloud-only files: Grape must hydrate or skip them, not hang), and zip folders opened in Explorer (virtual paths, which v1 should skip).
- Shift-drop never deletes the source.
- A drag out of the float shelf onto the Recycle Bin, plain or with Shift, never deletes the file.
- Explorer running elevated vs not.
- Two monitors at different DPI.
- Tablet/touch: Windows touch drags don't use the mouse hook path. Unsupported in v1, so make sure nothing breaks.
