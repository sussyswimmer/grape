# apps/desktop/src-tauri

The Tauri 2 app: windows, tray, `WheelController` state machine, IPC and settings. **Lane A (Claude Code) owns this.**

## Windows (UI windows, not the OS)
| Label | Purpose | Flags |
|---|---|---|
| `overlay` | full-display transparent wheel | transparent, no decorations, always on top, skip taskbar, unfocused, all workspaces, hidden at start |
| `settings` | preferences | normal window, opened from the tray |
| `float` | file shelf (Windows and macOS) | built in code (`src/float.rs`), on first use on Windows and at launch on macOS: transparent, no decorations, always on top, skip taskbar, tool window (Windows), accept first mouse (macOS), activatable, hidden at start |
| `toast` | progress and done messages | small, topmost, click → reveal |
| `panel` | a tool's options before it runs (Compress, Audio Channels, Normalize, Merge PDFs) | declared hidden in `tauri.conf.json`: transparent, no decorations, always on top, skip taskbar, tool window, activatable, not focused when shown, hidden at start |

The overlay's full spec is in `docs/ARCHITECTURE.md` → "The overlay window". `"macOSPrivateApi": true` is set in `tauri.conf.json` (a no-op since Tauri 2.12.1, but it must match tauri's `macos-private-api` feature). On Windows the Cargo feature `overlay-subclass` (default on) adds the tool-window and no-activate styles to the overlay and toast, and the tool-window style alone to the float shelf (`docs/DECISIONS.md` D11). On macOS the overlay and toast are hardened and shown through `grape_platform::macos` on the main thread (`orderFrontRegardless`, never key), and drops come from wry through `WindowEvent::DragDrop` (D18). The tool panel gets the shelf's bits on Windows, and on macOS level 99 and the one key window Grape makes (D31). On macOS the float shelf is hardened as `WindowRole::Shelf` (level 3, under every other Grape window, the overlay's collection behavior and the `Closable` bit for Cmd+W) and is key only after a click (D43).

## WheelController
- Implements the state machine in `docs/INTERACTION_SPEC.md` §1, exactly. Unit-test it with `grape_platform::mock` signal scripts. It's pure state, so it doesn't need a real OS.
- Lives in `src/controller.rs` (pure) and `src/wheel.rs` (wiring to the monitor, the drop target and the overlay).
- Inputs: `DragSignal`s (including `Escape`), the overlay's drop events (`grape_platform::DropEvent` from Grape's own drop target on Windows, `docs/DECISIONS.md` D13, or from wry's on macOS, D18), Pause, `Configure` (new keys and sounds from Settings, used from the next modifier; an open wheel isn't redrawn), and `wheel_painted` from the overlay.
- macOS-only rules sit behind `ControllerConfig` flags, `release_fallback` and `leave_ends_drag` (D18). Keep both off on Windows.
- Outputs: the events in `src/events.rs`, which follow `docs/design/m1-drag-wheel.md` §C and are tested against the UI's golden JSON in `ui/src/shared/fixtures/`: `wheel://open {seq, mode, anchor, scale, geometry, keys, sounds, content}`, `wheel://highlight {seq, index|null}`, `wheel://close {seq, reason}`, `toast://show`, `toast://hide`, the shelf's `float://view {items}` and `float://drag-ended {outcome}`, and the tool panel's `panel://open {seq, title, items, panel}` and `panel://close {seq}`.
- The toast (`src/toast.rs`) sits under the wheel (above it near the bottom of the screen), never takes focus, and hides itself after a few seconds unless it's a "working" toast. Clicks come back as `toast_clicked(id)`; only Rust knows the paths. On Windows it refuses drops; on macOS wry accepts a drop on it as a copy and ignores it, and it sits one window level below the overlay so an open wheel always covers it (D18).
- The float shelf (`src/float.rs`, Windows and macOS): Alt-drop (Windows) or Control-drop (macOS) on FLOAT puts the items on it after what's there (no path twice, at most 50; `actions.rs` says so in a toast when some didn't fit). The model (`Shelf`, managed) is pure, in memory only and tested; the page gets ids and names, never paths, and works by id through `float_view`, `float_remove`, `float_clear`, `float_reveal` and `float_drag_out`, granted only to the `float` window (`capabilities/float.json`). Everything but the OS calls is shared (`float.rs`'s `mod window`; each OS's calls are in its `native` module). On Windows the window is built off the main thread on first use (a lock like Settings'), hardened with `grape_platform::windows::harden_shelf` (tool window, no taskbar button or Alt-Tab, but activatable: the drag out needs mouse capture) and shown, resized and hidden only through `show_shelf` / `hide_shelf` on the main thread, never Tauri's `show`/`set_focus`, so opening it never takes focus; it refuses drops at creation and before every show. On macOS (D43) it's built hidden at launch (`float::build_at_launch`, from setup: wry activates Grape whenever it builds a webview), hardened with `harden_window(…, WindowRole::Shelf)` (level 3), shown, resized and snapped through `grape_platform::macos::show_shelf` (never key or activating; it records the app in front, the hide's fallback) and hidden through `hide_shelf` (activation handed back to the app the user was last in, which `build_at_launch` starts following with `follow_app_activations`, if a click made it key), with its frame read by `window_frame` in points; wry takes drops on it as a copy and ignores them, so its `DragDrop` arm is off there. It opens at the right edge of the drop's monitor, centered; an open shelf stays put and only changes height. Moved by its header, it snaps to a screen edge it was left within 48 px of, 300 ms after the last `WindowEvent::Moved` once no button is down (`float::on_window_event`). `float_drag_out` is async; on Windows it queues `grape_platform::windows::drag_out` (copy or link, never move) on the main thread, which blocks until the drop, then emits `float://drag-ended`; on macOS it queues `grape_platform::macos::drag_out` (copy or link, never move), which returns at once, and the outcome comes from AppKit's end callback (a drop on a Grape window is Cancelled). Logs carry counts and outcomes, never paths or names. Linux never builds it: Float says it's coming there.
- The tool panel (`src/panel.rs`, pure model in `src/panel/model.rs`, D31): `wheel::run` asks `panel::route_for` first. A drop on a v1 panel tool (grape-core's `ToolKey::has_v1_panel`: Compress, Audio Channels, Normalize Volume, Merge PDFs) opens the panel only when the wheel offers that tool for the drop (`model::offered`: `grape_core::wheel_content` with `settings::planning_features()`, the features `plan` uses, so the multi-OK rule holds: Audio Channels on one file, Merge PDFs on two or more, nothing a format's tools leave out) and `jobs::check_runnable` passes its default-params op: Merge PDFs when PDFium is found, Compress on JPG and PNG always, and Compress (MP3, M4A, WAV, FLAC, MP4, MOV, MKV), Audio Channels and Normalize Volume (MP3, M4A, WAV, FLAC) when FFmpeg is (D26). `GRAPE_PREVIEW_PANELS=1` (exactly `1`, QA) skips only the runnable check, so the four also open where they're offered but can't run (Compress on MP3s without FFmpeg), and their Run gets the usual info toast. Everything else goes straight to `jobs::submit`. One panel at a time: a new request replaces the open one (logged as cancelled). The page gets the panel's own seq, item ids `1..=n` and display names, never paths, and answers with `panel_current`, `panel_run {seq, order, choice}` and `panel_cancel {seq}`, granted only to `panel` (`capabilities/panel.json`). Rust ignores a stale or second run, refuses a bad order, a choice for another tool or a target `ToolParams::lufs_ok` refuses (−24…−10 LUFS in steps of 1, grape-core's `LUFS_MIN`, `LUFS_MAX` and `LUFS_STEP`, which the Normalize panel's spec carries too) ("Grape couldn't use that choice."), and on Run remembers the choice, hides the panel (then `panel://close`) and calls `jobs::submit_op` with the chosen `ToolParams` and order. Every show and hide is one reconcile queued on the main thread (`panel::sync`), never Tauri's `show`/`hide`/`set_focus`: on Windows `show_panel`/`hide_panel` (not activated when shown; the first click activates it; closing an active panel hands the foreground back), a "grape-panel-esc" thread polling Esc every 30 ms while a panel is open, acting only until the panel's window first has the focus (then Esc is the page's, and an Esc in another app is that app's) and never while a mouse button is down or was a sample before (`model::EscPoll`), and refusing drops before every show; on macOS `show_panel` makes it key and asks to activate Grape, `hide_panel` hands activation back. Alt+F4 is a cancel. `panel_cancel` is refused while a mouse button is down on Windows and macOS (that Esc belongs to a drag), and the page takes input again. Blur keeps it open; Pause (`cancel_open`) closes it and Quit forgets it (`shut`). The wheel's overlay is raised over it on every show (`raise_topmost`, Windows). Logs carry seqs, counts, the tool and reasons, never names or paths.
- Share passes the wheel's center to `file_actions::share` and words the `ShareOutcome` in `actions.rs`: no toast when everything went, "Sharing n of m" when some were left out, "Nothing to share" when none could go.
- The wheel opens pending and fills in with `grape_core::wheel_content` when the drop target's Enter brings the paths. A drop on a segment becomes a `RunRequest`: file actions run in `src/actions.rs`, conversions in `src/jobs.rs` (`build_selection` → `plan` → `run_job` on a worker thread, with the toast), and tools go through `jobs::check_runnable(op, items, sidecars)` too, which says "Not in this build yet" (or that a shipped helper is missing) for what can't run; a v1 panel tool it passes, on a drop the wheel offers it for, opens its panel first.
- **Job notes (D35, D26):** `JobOutcome::notes` carries facts, never words (`Note::LeftOut`, `PagesScaled`, `MetadataRemoved`, `Compressed`), and `jobs::finished` words them in the done toast's **title** (`noted`), first of: "2 links left out", "1 page drawn below 300 DPI", what Remove Metadata removed, or "62% smaller". Remove Metadata names each `MetaField` with `meta_word`, in the enum's order: location, camera, author, title, subject, keywords, comments, copyright, creator, producer, software, dates (both dates), XMP, IPTC, thumbnail, cover art, chapters, embedded media, other fields (also any field added later): "Removed location and camera", "Removed author, title and 3 more", or one name and a count past 32 characters ("Removed location and 4 more"; the title has 246 px, and the widest title there is, the fallback "Removed embedded media and 1 more", is 241.8 px in Inter). With none it's "No metadata found", or "No document metadata found" when the drop has a PDF (a PDF keeps page-level XMP and its images' metadata). Compress's sizes are summed over the drop's jobs into a whole percent, half up (`smaller`): no claim when nothing got smaller or by under half a percent, and never "100%" while a byte is left. The detail still names the output, or counts "files", "folders" or "items" (`several`; a PDF → images job may make either). Counts add up over the drop's jobs; macOS metadata left out of an archive is only logged. A fallback that every output took, or a failure, keeps its own title, and the notes are then only logged; when only some fell back, the notes keep the title. `Note`, `MetaField` and `ErrorKind` are `#[non_exhaustive]`, so every match on them needs a `_` arm. The log line carries counts, sizes and kinds, never a name or path.
- **Nothing to change (D26):** a job that ends `ErrorKind::NoChange` (already compact, already mono, no sound to remove, at the target loudness, too quiet to measure) wrote nothing and isn't a failure. A drop where every job ended so is an **info** toast, "Nothing to change", with the engine's own sentence as the detail for one job ("song.mp3 is already compact. Try Small."; an info toast's detail takes two lines, `toast.css`, enough for the reason after a name of about 40 characters, and so does a done toast's) or a count for several ("3 files already compact"). When others wrote something it's a done toast whose detail adds the count: "6 files; 2 already compact" (after "1 in Downloads\Grape" when some fell back, and in place of "its folder is read-only" when all did). Beside a real failure a `NoChange` job counts as done in "{ok} of {n} done". The words come from the drop's tool and params, never from the engine's sentence (`unchanged_words`): "already compact" (Compress), "already mono" / "already stereo" (Audio Channels), "had no sound" (Remove Audio), "unchanged" (Normalize, which ends so at its target and when too quiet, and anything else). The log says "nothing to change" with the kind, never the detail.
- Hit testing uses `grape_core::hit_test` with the drop target's global positions, converted to logical offsets from the anchor. Global positions are physical pixels on Windows and points on macOS, where `DisplayBounds.scale` is 1.0. Tauri's `PhysicalPosition` values on macOS are backing pixels, except wry's drop positions (points), so never pass one to the controller unconverted.
- **Watchdog:** if no drag signals or drop events arrive for 30 s while the overlay is visible, hide it.

## Settings
- `src/settings.rs`: the typed `AppSettings`, loaded once in setup (before `wheel::start`) from `settings.json` in the app data folder through `tauri-plugin-store`, and the Settings window's `settings_*` commands. The model (loading, the swap rule, the view, what to store) is pure and tested against the UI's golden `settings-view-*.json`.
- Loading is total: a missing or unusable value (wrong type, unknown key, a key or terminal app this OS doesn't offer, a relative path) falls back to its default, and keys that aren't three different ones all reset. Warnings name the key, never the value.
- The store ignores a file it can't load and writes over it at exit, so a `settings.json` that's there but can't be read or parsed is renamed to `settings.unreadable.json` (` 2.json`, … when taken; never over a file) before the store opens. If that rename fails there's no store at all. Parse errors are logged by kind and position only.
- A chosen fallback folder is planned with only while it's an existing folder; otherwise the default `Downloads/Grape`. Grape never creates a folder the user chose.
- The tool panels' memory: `tools.compress` (`"small"`, `"balanced"` or `"high"`) and `tools.normalize_lufs` (a target `ToolParams::lufs_ok` takes: −24…−10), loaded with the rest (warnings name the key, never the value) and saved by `settings::remember` when a panel's Run is accepted. They aren't in the Settings view.
- Every change applies at once and is saved at once: keys and sounds go to the controller (`Input::Configure`), haptics to the flag `wheel.rs` reads on every highlight, folders to the next job (`jobs::submit` plans with `settings::planning_settings`). A failed save is logged and reported, and the change still applies.
- Keys: Windows offers Shift / Ctrl / Alt (never the Windows key), macOS adds Command. Choosing a key another wheel has swaps the two, and the view carries a note saying so. Names come from `Key::name_on(Platform)`.
- The window never sends a path. Folders come from `grape_platform::file_actions::pick_folder` on a blocking worker, owned by the Settings window's HWND on Windows.
- Launch at login is `tauri-plugin-autostart`: a release build turns it on at its first launch only if nothing at all is stored (an unusable value doesn't count), there's a store, and `settings.json` wasn't unreadable at this launch; on macOS also not from `/Volumes/…` or an `AppTranslocation` copy (`settings::first_launch_rule`). On Windows the same release build, store and readable file also register it again when `true` is stored but the `Run` value is gone from HKCU and HKLM with no "off" in Task Manager (an uninstall that kept `settings.json`, or any other removal outside Settings and Task Manager; `grape_platform::windows::run_value`, never auto-launch's `is_enabled`); a value that's there, on or off, or names another program is left alone (D19). Debug builds never touch it on their own. The view shows the plugin's real state.
- Terminal app (`terminal_app`): Windows Terminal or PowerShell on Windows, Terminal or iTerm2 on macOS, the first being the default. `actions.rs` copies the choice out of `SettingsState` on the action's thread (`settings::terminal_app`) and passes it to `file_actions::open_terminal(dir, app)`, which keeps the fallbacks (PowerShell when `wt` can't start, Terminal when iTerm2 isn't installed).
- Welcome card: until "Got it" (`settings_dismiss_welcome`) stores `onboarding.done = true`, the view carries `welcome: true` and setup opens Settings once per launch, after `wheel::start`, through `ui_windows::request_settings`, in debug and release builds alike. Not when the store can't save (a test save fails), or it would open at every launch for good, and not when Grape started at login (launch at login passes `--at-login`, `settings::LOGIN_ARG`) (`settings::welcome_rule`). Changing other settings never dismisses it.
- The `settings_*` commands are granted only to the `settings` window (`capabilities/settings.json`). No window gets the store's or autostart's own commands.

## Rules
- The app crate is the only place `anyhow` is allowed.
- The settings store is `tauri-plugin-store`. Keep keys exactly as in `docs/ARCHITECTURE.md` → Settings.
- Sidecars go in `bundle.externalBin` with target-triple suffixes, set only by one sidecars overlay per OS that a build passes with `--config` (D25): `tauri.sidecars.windows.conf.json` lists `binaries/ffmpeg`, `binaries/ffprobe`, `binaries/bsdtar` and `binaries/grape-heif` and bundles `licenses/ffmpeg/`, `licenses/libarchive/` and `licenses/grape-heif/`; `tauri.sidecars.macos.conf.json` lists the first three with the first two folders. CI's installer and DMG jobs and `release.yml` pass them, with Grape's own FFmpeg (CI's `scripts/ffmpeg/build.sh` jobs, D24), bsdtar (D27) and grape-heif (D33) from the same run. Each overlay's `beforeBuildCommand` runs the gate `scripts/check-sidecars.mjs` first, which refuses any sidecar that isn't Grape's own build (the `-grape` marker; for grape-heif also the image helper protocol this checkout speaks, D41) or lacks its licenses, `SOURCE.md` or notices section, and the bundle puts them next to Grape's executable without the suffix (with the overlay, `tauri dev` has tauri-build copy them into `target/debug`, and fails while any file it lists is missing from `binaries/`). `scripts/fetch-sidecars.ps1` and `.sh` fill `binaries/` with FFmpeg and PDFium from `scripts/sidecars.lock`; bsdtar comes from `scripts/bsdtar/build.ps1 -Install` / `build.sh --install` or from CI's bsdtar workflow, never from the lock (D27). Never pass a second overlay that also sets `externalBin`: it would replace the array, not add to it (the PDFium overlays set only resources and frameworks, so they go with it). `src/sidecars.rs` finds them once in setup, only there (`{name}{EXE_SUFFIX}` in `current_exe()`'s folder; `grape-heif` on Windows only and `bsdtar` on both; on macOS the image helper worker is `current_exe()`, not a sidecar, so the log doesn't name it), never on `PATH` and never through the shell plugin, and every drop's `EngineCtx` gets a copy as `SidecarPaths`. The log names the ones found, never their paths. Each drop's `CancelToken` stays in `jobs::Running` until its thread ends: tray → Quit, `ExitRequested` with a code and `RunEvent::Exit` cancel them all (and any drop that starts after), and `Exit` waits up to 2 s for them to end, so no job outlives Grape.
- **The PDF worker (D29).** `src/main.rs` reads the first argument before anything else: `Grape --grape-pdf-worker` (`grape_engines::pdf::WORKER_FLAG`, exactly, right after the program name) runs `grape_engines::pdf::worker_main()`, one PDF job with its request on stdin and JSON lines on stdout, and exits with its code. No Tauri, window, tray, single-instance check or logger starts in that process, and it logs nothing. It reads `args_os`, never `args`, so an argument that isn't Unicode can't panic. Grape's own process never loads PDFium.
- **The SVG worker (D39).** `src/main.rs` also checks for `Grape --grape-svg-worker` (`grape_engines::svg::WORKER_FLAG`, exactly, right after the program name) before anything else, on every OS, and runs `grape_engines::svg::worker_main()`: one SVG drawn by resvg, its request on stdin and JSON lines on stdout, with no Tauri, window, tray, single-instance check or logger. It arms its own 2 GiB heap bound (the `WorkerHeap` allocator the PDF worker uses; `main.rs`'s copy is one of three, with the engine's two worker bins: change all three together). `src/sidecars.rs` gives every job `current_exe()` as `SidecarPaths::svg_worker` on every OS and doesn't log it. `jobs.rs` has no HELPERS row for it; SVG to HEIC or AVIF needs the image helper too, so on Windows without `grape-heif.exe` it gets that helper's row. The done toast words its notes (`noted`): "1 image left out" / "3 images left out" (`Note::ImagesLeftOut`, after an archive's left-out) and "Drawn smaller to fit" (`Note::DrawnSmaller`, after the pages below 300 DPI). The app's containment hook covers it as it covers the image helper; `remove_leftovers()` also removes stale `grape-svg-…` work folders.
- **The image helper (D33, D41: HEIC and AVIF).** `src/main.rs` also checks for `Grape --grape-heif-worker` (`grape_heif_proto::WORKER_FLAG`, exactly, right after the program name) before anything else, on every OS. On macOS `run_heif_worker` (OS-neutral, so a test runs it) calls `ImageIo::restrict_process()` (ImageIO restricted to the HEIF and AVIF types first thing, on one thread), arms the heap bound the PDF worker has at `grape_heif_proto::WORKER_HEAP_BYTES` (2 GiB; past it the worker exits 86, "needs too much memory"; ImageIO's own `malloc` isn't counted) and runs `grape_heif_proto::worker_main(&grape_platform::macos::heif::ImageIo)`: one HEIC or AVIF job through ImageIO, AVIF written by rav1e (grape-platform's `avif-encode`, which the app's `Cargo.toml` turns on for macOS only), the request on stdin and JSON lines on stdout, with no Tauri, window, tray, single-instance check or logger. A unit test runs the test binary as a child through `run_heif_worker` with a stand-in `restrict` and `serve`, so it checks the worker's own steps: the bound is armed after `restrict` and before `serve`, a block under 2 GiB is given, one over it ends the child with exit 86. Elsewhere it exits 2 at once and never starts a second tray app (Windows' helper is `grape-heif.exe`). `SidecarPaths::heif` is `grape-heif.exe` next to `Grape.exe` on Windows (bundled by `tauri.sidecars.windows.conf.json`, next to `tauri.pdfium.windows.conf.json`) and `current_exe()` on macOS. `src/contain.rs`'s `install()`, called once in setup before any drop, sets `grape_engines::set_contain` to a Job Object per helper on Windows (`grape_platform::windows::job`; nested without UI limits when Grape itself runs in a job, as under `pnpm tauri dev`, logged once) and does nothing elsewhere; `remove_leftovers()`, right after it on every OS, removes on a thread of its own the `grape-heif-…` work folders a crashed or killed Grape left in the temp folder (`grape_engines::remove_stale_work_dirs`), logging only the count. `jobs::check_runnable` says "Grape's image helper is missing / Reinstall Grape to work with HEIC and AVIF files." when only the missing helper stops a HEIC or AVIF drop on Windows (AVIF to and from the rasters, to PDF, HEIC ⇄ AVIF and HEIC Compress, D28, all need it, hence "work with"; AVIF has no tools in v1, so none is ever offered or run); elsewhere such a drop is "coming". The other shipped helpers have rows of their own in `jobs::HELPERS`, on Windows and macOS: "Grape's PDF library is missing", "Grape's RAR helper is missing" (bsdtar) and "Grape's media converter is missing" (`ffmpeg` or `ffprobe`), each with "Reinstalling Grape brings it back."; Linux ships none, so there every such drop is "coming". When several shipped helpers are missing and only all of them together would let the drop run (a PDF and a HEIC on Windows), it says "Some of Grape's helpers are missing / Reinstalling Grape brings them back.". A failed job's log line is its kind and the engine's detail with the job's paths, folders and file names replaced (`failure_log`); the user message, which names the file, never goes to the log.
- **PDFium** is found once in setup by `src/sidecars.rs` too, with the same `is_file` rule: `pdfium.dll` next to the executable on Windows (a `bundle.resources` entry of the `tauri.pdfium.windows.conf.json` overlay; `target\debug` in dev), `libpdfium.dylib` in `Frameworks` beside the executable's folder on macOS (`Contents/Frameworks`, from `bundle.macOS.frameworks` in `tauri.pdfium.macos.conf.json`; `target/Frameworks` in dev), and nowhere on other systems. The worker is `current_exe()`. Both are `SidecarPaths::{pdfium, pdf_worker}`; the startup log says `pdfium` was found or missing, never where.
- Plugins allowed so far: store, autostart, log, single-instance, shell (allowed for sidecars, though they don't need it), updater (opt-in, M7). Adding others needs a DECISIONS entry.
- Mac: `ActivationPolicy::Accessory`. Windows: no main window, tray only.
- **Never request network access** except the updater (golden rule 3).
